Reminder 注入系统 · 全景图

harness 往模型的消息流里注入的「旁白」——它们不是用户说的话，而是系统悄悄塞进去的提示、警报、历史替身。所有逻辑集中在 engine/reminders.py 一个注册表。

一句话理解：模型看到的对话，除了「你说的」和「它自己说的」，还夹着第三种消息——由系统注入的 旁白。这套系统就是在管：这些旁白长什么样（信封）、塞在哪（落位）、谁先谁后（优先级）。

1三种「信封」——旁白对模型的自我介绍

信封 = 包在文本外面的 XML 标签，告诉模型「这是什么性质的东西」。三种，各司其职：

<system-reminder>
实时警报（ALERT）
世界变了、或规则被重申。「你刚才的编辑报错了」「Stop hook 拦住你了」。权威单向：只能收紧约束，不能放松。
<archived_context>
历史替身（ARCHIVE）
被压缩掉的旧对话的「站位人」。自带标签说明它代表哪一段历史，所以不再二次套信封。
<cycle_carryover>
跨轮携带（CARRYOVER）
对话被整体重置（cycle）时，需要带到下一轮的简报种子。

2三种「落位」——旁白塞在对话的哪个位置

位置决定模型多重视它。越靠近结尾，注意力越强。

HEAD用户消息之前
会话级框架——「回答是基于这个前提的」。比如仓库当前状态、上次会话留下什么。
IN_HISTORY历史原位
替身要放在它替换掉的那段历史「原来的位置」，移到别处就等于篡改了过去的顺序。
TAIL消息最尾部
注意力最强的地方，只放实时警报。谁最紧急、最该「被最后看到」，就排最后。

4一条 reminder 是怎么被注入的

唯一正规路径：调用点只提供「哪条 spec + 内容」，套信封和贴溯源标签由注册表统一完成——避免历史上「套了信封却忘了贴标签」的老毛病。

1
调用点决定要注入：满足触发条件（如「turn 后有 LSP 诊断」），拿到 body 文本。
2
调用 reminder_message(spec, body) —— 唯一入口。
3
render() 先按 max_chars 截断，再套上 spec 声明的信封标签。
4
包成 Message.user(..., origin=spec.origin) —— 信封 + 溯源标签绑死，不会分家。
5
落位：HEAD 插到用户消息前，IN_HISTORY 插到历史原位，TAIL 追加到尾部。

5审计发现的两个问题

问题 B：SUBAGENT_DONE 溯源标签打错 ✓ 已修复
子代理完成有两条投递路径。turn 内路径走正规入口，溯源正确。但空闲后台路径只套了信封、没走正规入口，重入后被一刀切成 origin=REAL_USER（真实用户）——一条系统旁白被当成了「用户现在问的话」，会污染压缩、假旁白中和、ledger 归类。

修法（core.py:1914）：按 internal_kind == "subagent_background_done" 择一 origin，后台路径改回 REAL_USER → SYSTEM_REMINDER。信封本就对，只修溯源。测试全绿。
问题 A：优先级 / 落位「没人执行」 待处理
注册表声明了 placement 和 priority，但整个代码库没有任何地方读它们去排序。 TAIL 那批的实际顺序，是「turn 循环里谁的代码先跑就先追加」涌现出来的——今天恰好对，但哪天挪动了某段 append 的位置，顺序就悄悄变了，而 priority 数字还在那儿骗你「我是对的」。

本质：priority 现在是「注释级文档」，不是「真理」。也没有总预算机制——多条 TAIL 警报叠加时没有「超了就按优先级从低往高丢」的裁决。

方案：加一个单点收集器——TAIL 不再各自 append，先攒进缓冲，turn 收尾时按 priority 统一排序落位（可选加总字符预算，超了从低优先级丢并留一行提示）。这样 priority 从注释变成真理，「注册很多怎么取舍」变成一条集中、可测的规则。
