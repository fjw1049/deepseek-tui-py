审核结论

浏览器侧已经有控制者、控制代际、人工协助、操作回执、未知结果协调与恢复前观察；桌面侧已经有跨进程锁、取消监视、会话重置和人工交接。建议保留这些实现，补齐两条链路的共同状态契约。

现在用户最容易困惑的地方是：同样在“操作电脑”，浏览器与桌面显示不同的控制方式；预览、任务状态和操作结果也没有始终一致。扩充按钮或照搬另一款产品的菜单，会让这些差异更难理解。

产品目标：默认只回答四个问题——操作哪个目标、谁在控制、当前进展是什么、用户现在能做什么。工具名、运行时、捕获方式与协议细节保留在诊断层。

当前实现中需要先处理的问题

“静态确认”表示代码路径可以确定；不表示已经用真实应用复现。优先级用于安排升级顺序。

P1 · 静态确认

1. 切换目标或捕获失败后，旧画面可能仍被当成当前画面

A 应用已有画面，随后切到 B，但 B 没有窗口或捕获失败：卡片保留旧 canvas，新应用名却已更新。组件的 hasFrame 在本轮只从 false 变 true；错误提示又受 !hasFrame 限制，出现过画面后就可能不再显示捕获故障。

用户影响：用户看到的应用名、画面和工作状态可能互相矛盾，无法可靠判断 agent 是否在操作正确对象。

升级：画面携带目标身份与时间；切目标即废弃“实时”资格。保留最后画面时明确写“上一画面 · 12 秒前”。捕获失败不能被历史成功遮蔽；执行正常与画面断开应分别呈现。

证据：packages/workbench/src/renderer/src/components/cua-preview/CuaPreview.tsx:128；use-cua-window-stream.ts:62；store/cua-preview-store.ts:135。
P1 · 静态确认

2. 用户停止后仍显示“已完成”

预览 store 把结束与停止都转成 ended，没有结果字段；视图随后统一显示完成文案和绿勾。

升级：区分“操作已结束”“已停止”“未完成”“结果待确认”；只有结果确实得到验证时显示“已完成”。模型一轮结束或工具返回成功，都不能单独证明用户目标完成。

证据：store/cua-preview-store.ts:144；store/chat-store.ts:4082；components/cua-preview/CuaPreview.tsx:183。
P1 · 宿主缺口已确认，实际抢占需实机验证

3. 用户接管桌面期间，另一任务可能获得桌面锁

聊天 A 等用户完成登录时释放 CUA 连接与跨进程锁，只暂停自己的输入请求。聊天 B 可以进入同一个锁的获取路径。当前宿主没有单独保留“用户正在使用桌面”的全局所有权。

升级：人工接管时转入全局 user reservation；其他桌面任务进入等待。显式“继续”或结束接管后才让出。底层 LCU 是否有其他保护尚未验证，因此这里不能写成已复现的抢屏故障。

证据：src/deepseek_tui/engine/orchestrator/tooling.py:1357；src/deepseek_tui/cua/session.py:369、:427。
P2 · 静态确认

4. 一个局部错误可能让浏览器接管按钮消失

无效 URL、打开外部浏览器失败、打开输出目录失败等都可能写入通用 error。视图把它归为连接故障，并据此隐藏控制按钮，即使执行连接本身正常。

升级：分开连接错误、当前动作错误和输出展示错误。用户需要接管时，不能因为一个旁支动作失败失去入口；真正断连时显示可解释的不可用状态并保留停止路径。

证据：packages/workbench/src/renderer/src/components/BrowserWorkspace.tsx:569、:573；同文件 :554、:773。
P2 · 静态确认

5. 预览隐藏后，本轮无法主动重新打开

hidden-for-task 会保持到下一轮，未找到当前轮手动恢复入口。用户为了腾空间关掉预览后，反而无法再查看正在发生的操作。

升级：改成“收起”，留下“查看操作”入口。关闭预览仅改变可见性；停止执行必须是另一个明确动作。

证据：store/cua-preview-store.ts:51、:61；components/cua-preview/CuaPreview.tsx:260。

桌面未知结果Browser 有 durable receipt/unresolved；CUA 更多依赖中断后的文本提醒与重新观察。先建立 call 级 outcome_unknown，显示“操作可能已执行，待确认”，避免提供直接重复提交。

工程上如何升级，才能保持简单

Browser / Desktop 执行器 → 宿主控制与事件 → 同一操作面板 → 可追溯的结果

不必强行合并执行器。Browser 与桌面能力天然不同：一边有 tab、DOM 和导航，另一边有应用、窗口与系统输入。共同部分应是用户承诺与状态协议。

共同字段用途与约束
identitythread / turn / call / surface / window 或 tab。事件不属于当前目标时不能覆盖当前画面。
controlidle / assistant / transferring / user；接管必须有后端确认。桌面 owner 作用于整台宿主，浏览器按实际隔离资源定作用域。
phase + blocker执行、等待、观察确认、已结束分开；等待具体说明是用户操作、权限、占用还是连接问题。
observationcaptureEpoch、目标、capturedAt、live / stale / unavailable。新截图不等于任务完成；视频断开也不等于执行失败。
outcomecompleted / stopped / failed / unknown；“completed”由目标验证支持。未知结果先观察，不盲目重放有副作用的调用。
revision + recovery拒绝迟到事件；重连先读取宿主快照再接增量。前端只执行当前状态允许的恢复动作。

CUA 允许任意 JavaScript，因此第一版只做到 call 级结果记录。不要承诺能从任意脚本中恢复每次点击的事务语义。优先记清“未开始、已返回、可能执行但结果未知”，再接入工具证据与人工确认。

  1. 第一批：修复会误导用户的展示。停止结果、旧帧标记、局部错误分类、收起后重开。改动集中在现有 store 和组件，先用回归用例锁定行为。
  2. 第二批：补齐真实控制权。桌面用户占用、排队通知、接管确认、未知结果记录与恢复检查。没有后端协议时不先放一个“接管成功”的按钮。
  3. 第三批：统一操作面板。BrowserWorkspace 和 CuaPreview 共享状态文案、控制条和结果展示；人工协助成为面板内的阻塞态，聊天内只保留定位入口。
  4. 第四批：完善通用能力。按实际支持提供文件选择、上传下载、弹窗、跨应用跳转与可撤销授权；保留每类能力的真实边界。再根据使用反馈扩展平台和高级录制流程。

成功指标也应对应用户体验：接管从点击到确认的时间、发生误操作后能否安全停止、未知提交是否被重复、失败能否在原任务继续、用户能否找到正在控制的目标。先采基线，再决定数值目标。
