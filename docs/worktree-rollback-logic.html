01先建立全局认知：三个"根路径"与两个世界

整套逻辑的第一把钥匙，是理解前端如何在同一个会话里区分三个不同的目录。这由 packages/workbench/src/renderer/src/lib/workspace-path.ts 统一定义：

函数返回什么给谁用
resolveThreadFilesystemRoot() 当前线程的项目检出目录（用户真正的工程目录）。优先取线程自带的 workspace 字段，否则回退到全局工作区根。临时目录（/tmp 等）不会被抹掉。 文件预览、读写等一切需要"真实路径"的地方。
resolveThreadGitActionRoot() 用户驱动 Git 变更（切分支、暂存、提交、拉取、推送）的规范检出目录。目前直接等于 resolveThreadFilesystemRoot()。 GitBranchPicker、ChangeInspector、OperationContextDock 等所有会"写 Git 状态"的组件。
resolveThreadTaskReviewRoot() 只读的审查根：当线程 envMode === 'worktree' 时返回隐藏的 worktreePath，否则退回项目根。 ChangeInspector 在 context === 'conflicts' 时用它查看任务隔离副本里的文件改动。
核心设计：任务的代码在隐藏的 Git worktree 里执行（~/.deepseek/worktrees/<项目>/<threadId>），而用户看到的、用户手动 Git 操作的，永远是项目主检出 P。隐藏 worktree T 对 Git 面板来说只是只读的审查来源；把 T 的成果"交付"回 P 的动作叫 publish（发布），由后端按 ADR 0001 的同步/基线机制完成，前端只负责展示状态和收集用户决策。

两个世界的分工（来自 ADR 0001 的决策原文）：

  • 项目世界 P：用户驱动的一切 Git 变更（切分支、暂存、提交、pull、push）只作用于这里；
  • 任务世界 T：Agent 的工作副本。任务开始时从项目同步一份（含未提交/未跟踪文件），之后每轮维护基线 B，发布/回滚后再重新同步并原子记录新基线。

线程对象上与 worktree 相关的字段（packages/workbench/src/renderer/src/agent/types.ts:43 的 NormalizedThread）：

  • envMode: 'local' | 'worktree' — 该线程是否跑在隔离 worktree 里；
  • worktreePath — 隐藏 worktree 的绝对路径（后端字段为 worktree_path，兼容旧字段 associated_worktree_path，见 deepseek-runtime.ts:248）；
  • 发布状态四件套：publishPending / publishBlocked / publishConflicts / publishIssue，以及 publishRequestAction、publishWaitingOn。

这些字段怎么进到前端的？

两条路：

  1. 拉取 — threadFromJson()（deepseek-runtime.ts:238）在加载线程列表/详情时做归一化：把 env_mode === 'worktree' 映射成 'worktree'（其余一律按 'local' 处理），worktree_path ?? associated_worktree_path 归一成 worktreePath，并把 publish_issue 收敛为 'recovery' | 'failure' | 'missing' | null（publishIssueFromJson()，未知值返回 undefined 表示"旧版运行时没有此字段"）。
  2. 推送（SSE） — 运行中会收到 thread.updated 事件，deepseek-runtime.ts:1992-2086 从 thread 或 changes 载荷里逐字段解析 env_mode / worktree_path / publish_pending / publish_request_action / publish_waiting_on / publish_blocked / publish_conflicts / publish_issue，经 sink.onThreadUpdated 交给 chat-store.ts:1162-1216 做字段级合并（注意合并语义：ev.envMode ?? current.envMode 表示事件缺字段就保留旧值，只有显式给出才覆盖；worktreePath 特殊，区分 undefined 与 null——null 是有效的"worktree 已解除关联"）。合并后若 threadChanged 则更新 threads 数组，触发 React 重渲染。

整个前端到 Git 的调用分两条独立管道，互不混用：

主进程register-app-ipc-handlers.ts:1288-1374：先用 zod schema（app-ipc-schemas.ts）校验载荷，再调用 git-service.ts 导出的纯函数Python 侧 runtime 服务（/v1/threads/…），持有 worktree、checkpoint、基线、日志等真实状态

主进程 git-service.ts 的公共底座（git-service.ts:24-55）：

  • runGit(cwd, args, timeout=10s, maxBuffer=1MB) — 用 execFile（不是 shell 拼接，天然防注入）执行 git，并设置 GIT_TERMINAL_PROMPT=0 禁止交互式凭据提示卡死 UI；
  • runGitStdout(..., { allowNonZero }) — 变体，允许命令以非零码退出但仍取 stdout（diff 类命令常用，因为 git diff 用退出码 1 表示"有差异"）；
  • 大输出场景（diff/fetch/pull/push）显式把 maxBuffer 提到 DIFF_MAX_BUFFER = 50MB，超时提到 30s~120s。

03Worktree 管理逻辑（含发布冲突状态机）

3.1 任务的隔离与生命周期

worktree 的创建、同步、基线记录、发布全部由后端 runtime 完成，前端只做三件事：

  1. 展示：通过 envMode/worktreePath 判断当前线程是否在隔离环境，切换 UI（例如 Git 面板用只读审查根）；
  2. 预热：线程被选中且不忙时，chat-store.ts:2308 自动调用 warmActiveThread(id) → deepseek-runtime.ts:826 的 POST /v1/threads/{id}/warmup。后端在这里做"安全的工作区准备"——包括把项目文件同步进任务 worktree。它从不替用户选择文件版本；
  3. 决策：当后端报告发布被阻塞/冲突/失败/缺失时，弹横幅让用户做最小决策，再调用 POST /v1/threads/{id}/worktree/resolve 提交决策。

3.2 发布冲突状态机（publish-conflict-state.ts）

packages/workbench/src/renderer/src/components/chat/publish-conflict-state.ts 是一个纯函数状态机，把后端给的两路信号折叠成五种用户可见状态：

publishAttentionState(rawConflicts, publishBlocked, publishIssue?) →
  { kind: 'hidden'   | 'recovery' | 'failure' | 'missing' | 'conflict',
    conflicts: string[] }
kind含义触发条件典型文案色
hidden 一切正常，不弹横幅 无 issue，且 publishBlocked 为假或 conflicts 为空 —
recovery 未发布的工作：worktree 里有改动（相对基线 T − B），但找不到对应轮次的检查点，无法自动三方合并。需要用户决定"以谁为准"。 publishIssue === 'recovery'，或（兼容旧运行时）conflicts 里混入了标记串 '<unpublished-worktree-labor>' 琥珀色
failure 自动同步/发布流程失败，可重试 publishIssue === 'failure'，或旧标记 '<publish-failed>' 红色
missing worktree 目录丢失（被外部删除/移动）。这是"工作区丢失"而不是一个假文件，优先级最高。 publishIssue === 'missing'，或旧标记 '<missing-worktree>' 红色
conflict 真文件冲突：发布时任务改动与项目当前内容无法合并，列出具体路径 publishBlocked === true 且 conflicts.length > 0 琥珀色
兼容层细节（为什么代码这么绕）：旧版运行时没有结构化的 publish_issue 字段，而是把"原因"作为数组的一个元素塞进 publish_conflicts（例如 ['<missing-worktree>', 'src/app.ts']）。publishAttentionState 在 publishIssue === undefined（即检测到旧运行时）时，按 missing → recovery → failure 的优先级在数组里只移除第一次出现的那个标记——注释特别强调：另一个标记形状的字符串可能是合法文件名，不能误删。而结构化字段一旦存在（哪怕为 null），永远优先于标记串。
确认绑定的快照机制：publishRecoveryDecisionKey() 会把"recovery 状态 + thread.updatedAt + 冲突路径列表"序列化成一个 key。PublishConflictBanner 里用户做出的每一次选择都绑定这个 key（chat-store.ts:62-68 附近的 effect）：如果 runtime 推来一个更新的状态（路径集合或字节变了），旧的选择立即作废（decisionKey !== recoveryDecisionKey 时清空），且后端对过期 token 的处理是"刷新决策但一个字节都不写"。这实现的是 ADR 0001 的"把确认绑定到用户看到的精确 T − B 字节签名"。

3.3 PublishConflictBanner：横幅组件逐分支拆解

PublishConflictBanner.tsx 只在 activeThreadId 存在且 thread.envMode === 'worktree' 时渲染（组件第 70 行直接 return null）。渲染优先级从上到下：

  1. 成功反馈 — feedback === 'applied' 且无待处理状态：绿色条"草稿已应用"，2.4 秒后自动消失（useEffect + setTimeout）。
  2. 等待中 — !needsAttention && waiting：转圈 + "正在等待交付"，waiting = thread.publishWaitingOn || thread.publishRequestAction。表示用户（或另一进程）已经提交过决策，后端正在排队执行。
  3. recovery 分支（最复杂）：
    • 展示"未发布的工作"标题 + 冲突文件列表（最多 8 条，超出显示 +N）；
    • 提供两个选择按钮：保留项目版本（keep_project）与采用 Agent 版本（use_agent）；
    • 点任一按钮后先进入二次确认小面板（recoveryDecision 状态），确认文案按"有没有具体文件列表"分两种（文件数未知时用 publishRecoveryConfirmKeepProjectUnknown）；
    • 确认后调用 run(choice, recoveryToken) → resolvePublishConflicts(action, undefined, thread.updatedAt)。这里 thread.updatedAt 就是 recovery token，证明"我确认的就是我看到的那个快照"；
    • 只有列表为空时（文件数未知），只显示"保留项目版本"一个选项——无法展示具体文件时，偏保守的选择是唯一入口。
  4. missing 分支 — 红色条 + 一个"重试"按钮，点击走 retryMissingWorkspace()：调用 warmActiveThread()（即 warmup）让后端重新执行安全的工作区准备，然后 refreshThreads() 重拉线程。如果重试后仍是 missing 态，显示"重试失败"。注释强调：warmup 从不选择文件版本，若原始 worktree 真没了，状态保持不变（ADR 0001：保留精确关联，等路径回来，而不是伪造一个）。
  5. failure 分支 — 红色条 + "重试"按钮，走 run('apply') 重新尝试发布。
  6. conflict 分支 — 琥珀条列出冲突文件，三个动作：
    • 查看变更（左下）：openChangesPanel({ context: 'conflicts' }) 打开 ChangeInspector，此时 ChangeInspector 用 resolveThreadTaskReviewRoot() 拿到只读的 worktree 根来审查任务副本（ChangeInspector.tsx:932-936：changeRoot = isGitContext ? gitActionRoot : context === 'conflicts' ? taskReviewRoot || projectRoot : projectRoot）；
    • 保留项目：run('keep_project')；
    • 采用 Agent：run('use_agent')（高亮主按钮）。

run() 的公共防护（组件 73-98 行）：

  • submitting / busy / waiting 三态任一为真直接忽略点击，防双击与重入；
  • 调用后先检查 activeThreadId 是否已切换——用户切走了线程就不再 setState，避免串台；
  • 返回 result.status 分三种：'applied'（成功，清确认态、显示绿条）、'queued'（已排队，等待轮询/SSE 更新）、其他（'conflict' | 'pending'）——此时清掉 recoveryDecision，因为后端"刷新了决策但没有写入"，要求用户对新的快照重新确认。

3.4 chat-store 侧的 resolvePublishConflicts

chat-store.ts:3318-3349 是动作入口：

  1. 前置校验：无活跃线程返回 null；provider 不支持（旧运行时）则报 publishConflictUnsupported；
  2. 调用 provider.resolvePublishConflicts(threadId, action, paths, recoveryToken) → POST /v1/threads/{id}/worktree/resolve，body 为 { action, paths, recovery_token }（deepseek-runtime.ts:1513-1543）；
  3. 响应解析：status 只接受 'queued' | 'conflict' | 'pending'，其余一律按 'applied' 处理；必须返回 thread 对象，否则抛错；响应里还可能带 blocking_thread_id（后端告诉你"另一个线程挡住了这次发布"）；
  4. 成功后：workspaceDirtyTick + 1（广播"磁盘变了"，让 Git 面板/dock 自动刷新），并把返回的线程对象合并进 threads 数组。
三个动作在后端语义（ADR 0001）：apply / use_agent / keep_project。无论哪个，后端只允许作用于 T − B（相对基线的任务改动），绝不碰项目里用户自己的脏文件。三方合并失败的路径才成为用户可见的 conflict；恢复完成后重新同步 worktree 并原子记录新基线 B。ADR 同时强调：发布 followed by 回滚，不允许再把已发布的版本"还原"回来（不变量 4）。

04回滚逻辑一：会话回滚 rewind（含代码还原）

"回滚"在前端有两个独立能力（ADR 0001 明确"Conversation rewind 与 code rollback 是两个独立选择"）：

  • rewind（会话回滚）：把对话截断到某条用户消息之前，可选择同时把 worktree 里的代码文件还原到那一轮之前的状态；
  • restoreCode（单轮代码撤销）：对话不动，只把某一轮写的代码文件还原。

4.1 入口：编辑用户气泡 → 预览 → 确认

入口在 MessageTimeline.tsx:3077-3518 的 UserMessageBubble：

  1. 每条用户消息悬停出现铅笔按钮（ds-rewind-trigger），点击进入编辑模式（editing 状态），文本框内可修改原话；
  2. 点"重发"先走 requestResend()（3191 行）：
    • 不能还原文件的情形直接跳过确认：canRestoreFiles = activeThreadId != null && block.id.startsWith('item_')。只有以 item_ 开头的块才是已在 runtime 持久化的消息；本地乐观 id（u-…/q-…）从未落盘，没有可回滚的 runtime 状态，直接 commitResend(false)（仅回滚会话）；
    • 调用 GET /v1/threads/{id}/rewind-preview?before_item_id=…（deepseek-runtime.ts:1494）拿预览：files（会被还原的文件）、conflicts（第三方改过的路径，直接还原会覆盖别人的修改）、skipped、isGit、turns、missingRoots（checkpoint 根目录已消失的轮次）、noCheckpoint（范围内没有代码检查点的轮数）；
    • 预览为空 → 不弹窗直接执行。判定在 rewind-resend-confirm.ts:4：files.length > 0 || missingRoots.length > 0 || noCheckpoint > 0 才需要确认（连"缺检查点"也算需要确认的异常）；
    • 预览接口不存在（旧 runtime）或请求失败 → 弹一个 previewFailed: true 的确认框，正文换成"无法预览"版本。rewindResendConfirmModel() 保证无论预览成败，两个安全选项都在：['conversation_only', 'restore_code']（测试文件里的原话："Preview availability changes the explanation, never the user's two safe choices"）。

4.2 确认对话框的展示细节

确认框（portal 到 body 的模态，3442 行起）逐项处理预览数据：

  • 文件列表最多显示 8 条（REWIND_CONFIRM_FILE_LIMIT = 8），冲突/skipped 的文件排到最前（3256-3263 行的排序 comparator），保证被截断时最重要的信息仍可见；
  • 每个文件可能带标签：conflict 标签（琥珀）或 skipped 标签（灰）；
  • 有冲突时显示琥珀警告 + 一个"强制覆盖冲突文件"复选框（forceConflicts，默认不勾）；
  • 有 skipped 或 missingRoots 时提示"N 个文件不可还原"；有 noCheckpoint 时再提示"N 轮没有代码检查点可还原"；
  • 底部按钮：仅回滚对话（commitResend(false)）与 还原代码并回滚（commitResend(true, forceConflicts)）。当存在不可还原项时，还原按钮文案换成"还原可用部分"（rewindResendConfirmRestoreAvailable）。

4.3 commitResend → rewindAndResend：store 里的完整时序

commitResend（3168 行）把 restoreFiles && canRestoreFiles 与 force 收敛后调用 store 的 rewindAndResend(blockId, wireText, { restoreFiles, forceConflicts, retryDraft })。chat-store.ts:3140-3243 是这段核心逻辑，按注释分四步：

  1. 防重入：state.busy 时直接报 rewindBusyError；校验目标块确实是用户块。
  2. 先在 runtime 截断（注释原文：Truncate on the runtime first so the dropped turns are deleted from disk...）——顺序很关键：必须先让后端落盘删除，否则下次重载线程时被删的轮次会"复活"。只有 item_ 开头的块才需要调后端；rewindThread(threadId, userBlockId, restoreFiles, forceConflicts) → POST /v1/threads/{id}/rewind，body { before_item_id, restore_files, force_conflicts }。provider 不支持时报 rewindRestoreUnsupported 并中止。请求抛错时：仍在原线程就 setError，否则把编辑稿塞进 queueComposerRetryDraft 防丢失。
  3. 本地 UI 截断：truncateStateAtUserBlock(state, userBlockId) 生成 patch——删掉目标用户块及其后所有块、清 live 流式区、清轮次计时。若返回 null（截不了）直接放弃。restoredOnBackend 为真时 workspaceDirtyTick + 1，Git 面板监听这个 tick 自动刷新。
  4. 用编辑后的新文本发起新一轮：sendMessage(trimmed, get().composerMode, { expectedThreadId })。这里刻意沿用当前 composer 模式而不落回默认——注释说 UI 可能还停在 plan/ask 模式。

发送失败与部分成功的善后，是这段代码最细腻的部分：

  • 发送失败：runtime 回滚已持久、被编辑的气泡已删——这是不可逆的既成事实。为避免"一次瞬时发送失败吃掉用户的草稿"，把补丁里的旧状态（blocks/liveReasoning/liveAssistant/轮次计时）原样放回 store，并把新文本放入 queueComposerRetryDraft，返回 false；
  • 发送成功但文件还原有遗留：解析 RewindResult（见下），把 conflictedFiles ∪ skippedFiles 与 missingRoots.length 取最大值作为未解决计数，>0 时提示"已用 N 个未解决项完成"（rewindResendCompletedWithUnresolved）。

4.4 RewindResult：后端如实报告文件结局

agent/types.ts:75：

字段含义
restoreFiles本次是否执行了文件还原（回显请求参数）
restoredFiles成功还原的文件
mergedFiles通过三方合并还原的文件
conflictedFiles冲突、未被强改的文件
skippedFiles被跳过的文件
missingRoots已消失的 checkpoint 根目录（对应轮次的文件还原整体跳过）

解析层（deepseek-runtime.ts:1456-1470）做了向后兼容：老 runtime 的 rewind 响应只有顶层 ThreadRecord、没有 rewind_result 对象——此时返回 null，调用方按"无文件结局信息"处理（对应测试 rewind result compatibility）。字符串列表统一走 stringListFromJson，字段名缺失时还有备选名（restoreCode 处的 'restored'/'skipped' 同理）。

4.5 rewindToMessage：只回滚、不重发

chat-store.ts:3245-3287 是同族的另一个动作，逻辑与 rewindAndResend 的前三步相同（runtime 先截断 → 本地截断 → 刷新 tick），但不发新消息。特有防护：如果用户在 await 期间切换了线程，直接 return——注释说明"后端回滚对源线程已持久，新激活的任务不受影响；重新选中源线程时会从权威 runtime 状态重建"。

05回滚逻辑二：单轮代码撤销 restoreCode

入口是"本轮变更摘要卡"上的撤销按钮（MessageTimeline.tsx:1280-1333 的 TurnChangeSummary 区域）：

  • canUndo = Boolean(userBlockId?.startsWith('item_'))——同样只对已持久化的轮次生效；
  • 点击先弹 confirmUndo 二次确认，确认后 undoCode() 调 store 的 restoreCodeAt(userBlockId)；
  • store 侧（chat-store.ts:3289-3316）：busy 时拒绝；本地块直接返回 null（注释：本地块从未持久化，没有可对照还原的 runtime 状态，对话保持不变）；provider 不支持则报错；然后 POST /v1/threads/{id}/restore-code，body 只有 { before_item_id, force_conflicts }；
  • 返回 { restoredFiles, skippedFiles }，成功后同样 workspaceDirtyTick + 1 刷新 Git 面板；UI 用 turnChangeUndoSuccess 文案汇报"还原 N 个文件、跳过 M 个"。

与 rewind 的关键区别：restoreCode 不动对话。后端做的是"把该轮 checkpoint 记录的前镜像写回 worktree"，且按 ADR 0001 用 compare-and-swap 语义：先验证整个还原计划 → 每个路径写入前再校验一次签名 → 写后校验 → 只回滚"仍然是我们的字节"（内容、类型、可执行位都参与判定），避免覆盖用户或第三方在还原窗口期内的新改动。还原后后端重新同步 worktree 并记录新基线；成功回滚会刷新隐藏 worktree，之后 warmup 才能继续跑。

06用户驱动的 Git 操作与保护机制（主进程）

这条线在 git-service.ts（约 1360 行），处理的是 GitBranchPicker / ChangeInspector 面板上的用户操作。它们只作用于项目检出根，与隐藏 worktree 无关；但主进程里有两处逻辑与"worktree 世界"直接相关，值得细看。

6.1 managed worktree 的 detached HEAD 推断

git-service.ts:212-220 的 resolveCurrentBranch()：

async function resolveCurrentBranch(cwd) {
  const direct = (await runGit(cwd, ['branch', '--show-current'])).stdout.trim()
  if (direct) return direct
  // Managed task worktrees use detached HEAD. The nearest recently active
  // local ancestor is the branch the task was started from.
  const merged = await listLocalBranches(cwd, true)   // --merged=HEAD, 按提交时间倒序
  return merged[0]?.name ?? null
}

任务 worktree 天生是 detached HEAD（branch --show-current 返回空）。此时用"包含 HEAD 的、最近活跃的本地分支"当作展示用的推断分支。它只用于展示与推断对比基线（inferredBranch、recommendedBase，见 getGitBranches() 305-311 行），不改变 detached 事实——GitBranchesResult.detached 仍为 true，ChangeInspector 据此把 Git 变更面板置为只读（canMutateGit = gitBranches.ok && !detached，ChangeInspector.tsx:963）。resolveRecentAncestorBranch()（262-279 行）进一步产出 recommendedBase：若当前在默认分支则返回 null（没必要比较）；否则在 merged 列表里找第一个"不是当前分支、且 commit 不等于 HEAD"的最近分支——这正是分支对比视图（scope 'branch'）里"拿最近祖先当对比基线"的直觉。

6.2 protectRuntimeCheckout：禁止切走开发中的运行时检出

git-service.ts:68-97。当应用以开发模式运行（ELECTRON_RENDERER_URL 与 DEEPSEEK_REPO_ROOT 两个环境变量都存在）时，switchGitBranch / stashAndSwitchGitBranch / createAndSwitchGitBranch 都会先调用 protectRuntimeCheckout(cwd)：

  1. 分别对目标工作区与正在运行本应用的仓库根执行 git rev-parse --show-toplevel，并经 realpath 解析符号链接；
  2. normalizeCheckoutPath() 在 Windows 上统一转小写再比较；
  3. 若两者相同 → 返回 { ok: false, reason: 'runtime_checkout' }，用户看到 gitRuntimeCheckoutSwitchBlocked 文案。开发中的 app 正跑在这个检出上，切分支会把脚下的地板抽掉。

集成测试（git-service.integration.test.ts:57-105）专门验证了这一点：用一个真正的 git worktree add 建出的独立检出可以正常切换，而主检出被拒绝且不留任何副作用（没有新分支、没有 stash、脏文件原样保留）。注意：这只是普通的 git worktree 独立检出场景，真正的任务 managed worktree 由后端创建与守护，前端从不对其执行写操作。

6.3 脏工作区切分支的三段式交互

GitBranchPicker 上点一个分支 → window.dsGui.switchGitBranch(root, branch) → IPC git:switch-branch → switchGitBranch()（git-service.ts:368-396）：

  1. 先试 git switch，失败（且不是脏工作区错误）则退回 git checkout（兼容旧版 git）；
  2. 识别脏工作区错误靠正则：/would be overwritten by (checkout|merge)/ 或 /commit your changes or stash them/ → 返回 reason: 'dirty_worktree'；
  3. 前端 GitBranchPicker.tsx:201-206 收到 dirty_worktree 后关菜单、弹出居中警告框，内含一个 「stash 并切换」按钮；
  4. 用户点它 → stashAndSwitchGitBranch()（git-service.ts:398-451）：
    • git stash push --include-untracked -m "workbench: auto stash before switching to X"（30s 超时）；通过匹配 "No local changes to save" 判断是否真的存了东西（stashed）；
    • 切分支失败 → 先 stash pop 把用户改动还回原分支再抛错（pop 再失败也静默——stash 还在栈里，可用 git stash pop 手工恢复，绝不丢数据）；
    • 切换成功后 pop，pop 冲突 → 返回 reason: 'stash_pop_conflict'，前端显示 gitStashPopConflict 警告并刷新分支列表。

6.4 其余用户操作一览

操作主进程函数关键细节
读分支状态 getGitBranches() refreshRemote=true 时先 git fetch --prune（120s/50MB），fetch 失败不阻塞——错误放进 remoteRefreshError，本地分支状态照常返回。随后收集：当前分支、推断分支、本地分支列表（按最近提交排序）、默认分支（上游 remote HEAD → origin/main → origin/master → main → master 逐个尝试）、recommendedBase、脏文件计数（porcelain 行数）、upstream 与 ahead/behind 计数。
新建并切换分支 createAndSwitchGitBranch() 先 check-ref-format --branch 验证分支名合法性，再 switch -c（失败退 checkout -b）。
读工作区改动 getGitWorkingChanges() 四种 scope：working-tree / staged / unstaged / branch。porcelain v1 逐行解析（parsePorcelainEntry，处理 ">"转义与 a -> b 重命名），diff 按文件切分（splitUnifiedDiff），untracked 文件用 git diff --no-index /dev/null path 造补丁。带指纹缓存：HEAD + porcelain + 每个改动文件的 (mtime,size) 组成 fingerprint，最多缓存 24 个根（LRU 淘汰最旧）；写操作（stage/unstage/commit/pull）后用 invalidateWorkingChangesCache() 按前缀失效。
暂存 / 取消暂存 stageGitChanges / unstageGitChanges 路径安全闸 isSafeGitPath()：拒绝绝对路径、含 .. 的段、含 \0；50 个一批执行 git add -- …。unstage：有 HEAD 用 restore --staged（失败退 reset HEAD --），无 HEAD（空仓库）用 rm --cached --ignore-unmatch。
提交 commitGitChanges() 不带 paths 时遵守标准 Git 流：index 就是提交选择，注释明确"绝不从 Commit 按钮静默暂存工作区改动"；无暂存内容返回 nothing_to_commit。带 paths 时走 commit --only -- …，注释说明 --only 保证"之前暂存但未被选中的文件"不混入本次提交。
pull / push pullGitBranch / pushGitBranch pull 强制 --ff-only（注释：工具栏动作绝不引入隐式 merge commit），分叉返回 diverged；push 前先算 ahead/behind，behind>0 直接拒绝（behind_remote），无 upstream 时自动 push --set-upstream（优先 origin）。两者都先检查 attached branch，detached HEAD 直接拒绝。
提交日志 getGitLog() topo-order 最近 200 条，NUL 分隔解析（%H%x00%P%x00%s%x00%an%x00%at），同时读 upstream 的 ahead/behind；当前分支 detached 时退回 HEAD。
为什么这些操作在任务 worktree 模式下仍然安全？因为所有写操作都走 resolveThreadGitActionRoot()（项目检出）。即使你在任务会话里点了"切分支"，切的是项目；隐藏 worktree 的入站更新只有一条通道——后端的 journal 化项目→任务同步（ADR 0001）。Read-only 审查根（resolveThreadTaskReviewRoot）只出现在 conflicts 审查这一种 context。

07ADR 0001 设计决策与八条不变量

docs/adr/0001-task-worktree-sync-ownership.md（2026-08-30，Accepted）是这两条逻辑的"宪法"。背景：任务跑在隐藏 worktree，而项目在任务开始前可能就有 staged/unstaged/untracked 改动——Git status 本身无法判断"谁改的"（项目改动被复制进任务副本后，相对任务 HEAD 依然是脏的）。

核心决策：持久化基线 B

每次成功的项目→任务同步后，为该任务 worktree 记录一个基线 B，内容包括：worktree 的 HEAD、每个与 HEAD 有差异的路径、以及每个路径的内容+类型+mode 签名。据此把当前任务状态 T 分三种情况处理：

状态判定处理
干净T == B静默从项目刷新（含项目脏文件与 untracked），用户无感
有检查点某轮 checkpoint 记录了 T − B走既有三方合并发布；只有无法合并的路径才是用户可见冲突
无检查点的偏离T != B 但无 checkpoint两份都保留，进入 recovery。恢复只允许作用于 T − B 路径，绝不作用于所有脏路径

其余决策（与前端直接相关的已加粗）

  • 用户驱动的 Git 操作只作用于项目检出 P；隐藏 worktree 对这些控件是只读审查来源；
  • 发布/冲突解决/代码回滚后：重同步任务 worktree + 原子记录新基线；
  • 多文件入站同步前先落盘同步 journal（源/目标 commit + 每路径 before/target 签名）。重启后只有当每个路径仍处于两个签名之一才允许续写；出现第三种状态 → 进 recovery，绝不猜测归属；
  • recovery 确认绑定到用户看到的 T − B 精确字节签名；路径集或任一字节变了就刷新选项且一字不写（前端由 publishRecoveryDecisionKey + recovery token 实现）；
  • 首次项目写入前先落盘发布 journal（项目根 + checkpoint 不可变前后镜像）；所有写入成功才算 apply 完成；崩溃重启会重试未完成的 apply、跳过已完成的 apply，且绝不从"可能已被自己写过的字节"重建前镜像；
  • 每个 checkpoint 绑定它捕获的任务字节签名，发布前与发布中反复校验——防止迟到的后台编辑被悄悄算进更早的一轮；
  • checkpoint 还原用 CAS：全计划验证 → 写前逐路径复验 → 写后校验 → 只回滚"仍是我们的字节"（内容、类型、可执行位都参与）；
  • worktree 目录消失：保留精确关联，进入 missing 态等它回来；初始隔离创建失败则让任务准备直接失败，绝不静默写进项目检出；
  • 自动清理用 Git 最终的 clean-worktree 检查且不带 force：检查与删除之间到达的文件保住任务副本；force 只留给显式授权的用户丢弃；
  • 持久化的 recovery 标记是"待复核的证据"而非永久真相：基线证明任务无未记录改动时，标记自动清除；
  • ADR 之前的旧 worktree 无基线：只有当每个脏路径与项目逐字节相同、且任务 commit 可从项目到达时才允许自愈；模糊的旧状态一律保护。

八条不变量（逐条翻译成前端行为）

#不变量对应前端实现
1没改任何文件的任务绝不弹代码恢复提示无 issue 且未 blocked → hidden，横幅不渲染
2项目的新改动不会因为被复制进隐藏副本而变成任务所有recovery 仅针对 T − B；后端基线机制
3恢复绝不应用/丢弃 T − B 之外的路径conflict 横幅只列出冲突路径，决策 API 带 paths
4发布后再回滚，不允许把已发布版本又"还原"回来发布成功即清 recoveryDecision；后端基线刷新
5有 pending/blocked/failed/recovery 状态的空任务不会被复用成新任务后端线程生命周期管理
6项目写入跨进程串行化（POSIX 与 Windows）后端发布 journal
7崩溃/取消不能把部分同步变成"任务劳动"同步/发布 journal + 签名复核
8符号链接与文件 mode 按路径身份处理（或保持未解决），文本发布/回滚代码绝不跟随签名包含 mode/type

ADR 还有一条对前端 UI 的直接指令（"User-facing states" 一节）：正常同步不可见。UI 只在四种情况打断用户——真文件合并冲突（带具体路径）、自动同步失败（带重试）、经核实的无检查点任务路径（带文件列表与确认）、任务 worktree 丢失（按"工作区丢失 + 安全复查"呈现，而不是伪装成一个文件）。原因与冲突文件路径分开存储，因此任何合法文件名（哪怕长得像标记）都可表示。.worktreeinclude 显式纳入的忽略文件同样参与基线规则；未被策略选中的忽略文件不在托管交付契约内。

09细节清单：容易被忽略的边角

路径与身份

  • worktree_path 有两个后端来源字段（旧 associated_worktree_path），解析顺序 worktree_path ?? associated_worktree_path；
  • env_mode 归一化是"白名单式"：只有字面 'worktree' 才映射为 worktree，其他一切（包括缺失、乱值）都按 local；
  • SSE 合并语义：undefined = 保留旧值；对 worktreePath 来说 null 是有效值（解除关联），不能与"未提供"混淆；
  • resolveThreadFilesystemRoot 刻意不抹掉 /tmp 类临时目录（文件预览需要真实路径），而 resolveActiveThreadWorkspace 会抹掉——两个函数用途不同，别混用。

回滚的边界条件

  • 本地乐观块（u-/q- 前缀）从未持久化：rewind 与 restoreCode 都直接跳过后端调用，且 restoreCode 显式返回 null 不报错（注释：对话保持不变）；
  • canRestoreFiles 的注释点明 restore 的写入目标是记录的执行根：发布成功后该根就是项目本身；副本消失时该轮文件还原被跳过（missingRoots）；
  • rewind 前必须在 runtime 先截断，否则被删轮次会在下次线程重载时"复活"；
  • rewind 后重发沿用当前 composer 模式（plan/ask 等），不落回默认；
  • 发送失败的善后是"恢复 UI 到截断前 + 草稿回队列"，因为 runtime 回滚已不可逆，不能再让用户丢字；
  • 预览失败不降级为"仅回滚对话"——保持两个选项，只是把解释文案换成 preview_failed 版本（有专门单测锁住这个行为）。

发布/恢复的边界条件

  • 旧运行时的原因标记混在路径数组里；解析时只移除第一次出现的那个标记，另一个标记形状的字符串可能是合法文件名；
  • 结构化 publish_issue 一旦存在（含 null），永远压过标记串推断；未知 issue 值 → undefined（视为旧 runtime，触发标记推断）；
  • recovery 且文件数未知（列表为空）时，只提供"保留项目"一个按钮——无法展示清单时默认保守；
  • recovery token = thread.updatedAt；任何状态更新使 decisionKey 失配即作废选择；后端对过期 token 的策略是"刷新不写入"；
  • resolve 响应 status 白名单外一律按 'applied'；'conflict'/'pending' 会清掉用户的确认态，强制重新确认；
  • missing 重试只会"再跑一次安全准备"：若 worktree 真的没了，状态不会变化（也不会伪造文件），重试后仍 missing 就显示失败反馈；
  • 横幅只在 envMode === 'worktree' 的线程出现；local 线程永远不会渲染它。

主进程 Git 的防御细节

  • execFile 而非 shell 拼接，参数数组天然免注入；GIT_TERMINAL_PROMPT=0 防交互挂起；
  • 三类失败原因在每个入口都归一：not_git_repo / git_unavailable(ENOENT) / error，前端据此展示对应文案；
  • runtime checkout 保护会 realpath 两个根再比较，Windows 上大小写不敏感；保护生效时零副作用（无分支、无 stash、工作区原样）；
  • stash-and-switch 的失败回滚链：切失败 → pop 回原分支 → 连 pop 都失败也只静默（stash 仍在，可手工恢复），绝不丢弃用户改动；
  • 路径安全闸拒绝绝对路径 / .. 段 / NUL 字节；批量操作按 50 个/批切分；
  • 提交的哲学：不带 paths 时空暂存区报错而不自动暂存；带 paths 时用 --only 防止把别的暂存内容夹带进提交；
  • pull 永远 --ff-only，push 先查 behind——工具栏按钮绝不制造隐式 merge 或被远端拒绝的意外；
  • detached HEAD 的推断分支仅用于展示/比较基线；任何 Git 变更面板在 detached 下自动转只读（canMutateGit）。
