## 1. 投递：分清执行结果、发送尝试和当前配置

| 问题 | 修复后的行为 | 证据 |
|---|---|---|
| N1 明确拒收仍用旧配置 | 仍在发送前写日志；明确未发送后标记下次重试刷新配置，保留该次执行的原正文。结果不明时不自动重发、不换目标。 | 真实 localhost HTTP：旧 key 收到 400，改配置后第二次访问新 key；修改任务结果也不改变重试正文。 |
| N2 默认 webhook 凭据扩散 | 新快照不复制企业微信 key，保存目标指纹。运行记录、待确认列表以及工具返回的运行记录使用公共脱敏序列化。HTTP 异常写入日志时不带凭据 URL。 | 虚构默认 key 在实际 run JSON 和两类公共序列化结果中均不存在。 |
| uncertain 后恢复同一失败任务 | 将旧待确认发送保存为独立记录，新执行重置自己的投递状态。确认旧消息收到，不会吞掉新结果；重投旧消息，也不会冒充新结果。 | retry/received 两个分支分别验证旧、新正文和状态。普通“立即运行”本来就创建新 run ID。 |
| 本地 notify 也需人工确认 | 本地通知用稳定 delivery_id 对应消息 item，失败可有界重试；写入后回执失败、进程遗留 sending 都按同一 item 恢复。 | 实际会话存储：先写入后抛错，再从磁盘 sending 记录恢复，只保留一条通知。 |
| N5 每轮重复读历史记录 | 一次锁外扫描移至线程，跳过已经完成投递且无需回写的成功记录；可变记录仍在单 run 锁内重读。 | 对真实已 sent 的记录计数：一次对账读取从 4 次降到 1 次。未声称大型仓库延迟已有基准。 |
| N6 慢投递阻塞其他讨论 | 讨论改用对应 run 的锁，无关运行不再争用全局对账锁。对账批次仍串行，同一 run 的发送和修改仍互斥。 | 慢发送保持等待且全局对账锁仍持有时，另一 run 能完成讨论创建和结果回写。 |

**兼容边界：** 旧快照仍可读取；通过公共序列化立即脱敏，再次保存时移除旧快照中的 key，没有批量改写全部历史文件。用户显式配置在 automation / trigger run.delivery 中的目标仍保留内部可用配置；本轮消除的是快照额外复制和运行记录对外泄露，并未引入凭据保险库。如果 uncertain 的企业微信目标凭据已经更换，需恢复原目标后才能重投；程序不会默默改投当前新接收方，界面显示原因。

## 2. 前端和任务生命周期

- 待确认列表、自动化列表和渠道状态独立处理加载结果。待确认接口失败只在其区域提示，保留主列表和上次已知的待确认记录；渠道状态仍可更新。
- N3：正在执行的 durable task 阻塞等待其他未结束的 durable task 会立即收到明确错误，避免占用单 worker 空等。主会话的有界等待、子代理/进程等待、取消等待后后台任务继续执行均保留。
- D2：失败、取消和异常退出保留当前用户请求与已完成工具结果；缺失结果的工具调用补充“结果未记录，可能已有副作用”的错误说明，不伪造成功，不宣称撤销文件修改。完成结果先记录，再发送事件，减小硬取消时丢失事实的窗口。
- D19 fork_context：子代理可继承当前轮已完成的上下文；未完成的整批工具调用不传入，保持调用与结果配对。
- D11：流错误或超时后重采样，被放弃的工具调用会收到未执行的结束事件，前端不会留下永远运行的条目。

## 3. 权限、模式和工具闭环

- N4：可信只读 MCP 名单只在 ask/plan 中提供对应豁免；agent/yolo 继续遵循各自审批策略。模型工具名称通过 `model_name` 返回；未发现的名单项提示核对，精确匹配，不猜测授权。未因“只读”就假定服务支持并行。
- 空 MCP 配置不再挂三个资源工具；已配置但尚未发现的服务保留发现入口。
- 同轮切换模式会重新构造系统提示词、同步审批状态、重新准备 CUA 和工具目录。ask/plan 或禁用 CUA 时关闭会话并清理工具、缓存提示与上下文状态。
- `/yolo` 使用统一切换入口，真正切换模式，保留 goal 限制和退出后的审批恢复机制。
- D4：`note(action="read")` 提供显式读取，最多读取最近 64 KiB；旧 `note(content=...)` 继续追加。接入用户 `notes_path`，项目配置不能重定向它。ask/plan 只能读，不默认把全局笔记注入所有项目。
- D5：按名加载 skill 后，只允许读取该 skill 目录的配套文件；列出有界的子目录入口。越界符号链接、敏感文件和写入仍受限制，未授权执行 skill 脚本。
- D8：grep 遍历超预算时返回已经找到的结果和 incomplete/truncated 标记；参数错误和未取得结果的正则超时仍明确失败。
- D12（第五轮更正适用范围）：标准运行时仍为 `network_policy=None`，应用没有启用此可选策略。此前添加的是显式注入 `NetworkPolicyDecider` 时的 Web 审批桥，不应视作默认用户路径的缺陷修复。注入后批准才发请求，拒绝/无人值守不自动放行。第五轮修复此路径复制 metadata 导致的超时计数丢失，未新增应用配置。
- N7：删除私有的旧 fork/exec helper，改测实际 asyncio PTY 路径。检查又发现后台启动、超时转后台两处仍引用旧 `pid`，已改为真实进程 PID，并增加实际进程验证。公开兼容函数、旧数据适配及仍可通过 API 使用的 profile 保留。

## 4. 真实验证范围

这次使用项目 `.venv` 的真实依赖，没有占位 croniter/FastAPI/regex，没有调用付费模型或真实第三方消息渠道。模型响应采用可控脚本，验证的是实际 Engine 的确定性处理逻辑。

实际运行的场景包括：

- localhost HTTP 的 400→修改目标→成功重试，原正文保持一致；网络审批批准和拒绝两条路径。
- 真实任务 worker、排队任务、文件写入与硬取消后的对话历史。
- stdio MCP 子进程和严格 never 审批。
- 真实临时笔记文件、工作区外 skill 文件、敏感路径、符号链接和 grep 已取得的结果。
- 前台/后台/超时转后台 PTY 子进程及环境变量隔离。
- 实际会话磁盘存储、投递日志恢复和慢投递期间讨论操作。
- 原生 Electron 窗口中的 React DOM → IPC → localhost FastAPI → 磁盘投递记录：点击“已收到”和“重新投递”，得到 sent / pending 状态。

原生 CUA 对操作系统应用的操控、本机以外安装包和真实飞书/邮件/企业微信渠道不在这次验收中。CUA 这里验证生命周期和目录/提示同步，没有宣称完整实机操控通过。

## 5. 留给后续审核的事项

| 事项 | 目前取舍 / 原因 |
|---|---|
| 非阻塞轮询仍可能到 200 轮 | 保留已有轮次/时间/重复结果限制和 block=true 指引；没有把“仍有进展”误判成死循环。是否另设 peek 次数或费用上限，需要明确预算契约。 |
| D9 探测 shell 的非零退出 | 保留真实退出码。未采纳“exit=1 且 stderr 为空即成功”的规则，它会掩盖真实测试失败。可以单独设计显式 expected_exit_codes，但需同步前台/后台语义。 |
| D10 soft-resume 固定恢复预算 | 本轮未扩大窗口；它是恢复成本策略，不等于供应商模型识别错误。全文指针及恢复预算命名/约束的一致性仍需单独处理。 |
| 非 UTF-8 全量覆盖 | 继续拒绝不安全的文本覆盖。若要支持，需要按字节快照与恢复，不宜只把 decode 错误吞掉。 |
| dist/build 默认过滤 | 保持默认；是否纳入生成物和如何提示搜索范围属于产品取舍。 |
| stdout/stderr 重复存储、token 重复序列化 | 未取得性能收益基准或证明所有消费者都不依赖这些字段，暂不删除结构化数据/增加复杂缓存。 |
| MCP 并行执行 | 可信只读不等于会话并发安全，未自动开启。 |
| 公开旧接口、单次投递 fallback、模块拆分 | 按此前要求保留兼容；没有 manager 的旧投递入口仍缺少持久化确认能力。大模块拆分未混入本次可靠性修复。 |
| 无人值守 cron 工具范围 | 保持此前行为，仍需单独明确允许哪些写入、网络和 MCP 行为。 |
| 历史凭据副本 | 旧快照按读取脱敏、再次写入清理；没有批量清理所有历史文件或重构显式目标配置的凭据存储。 |
| 实机验收 | 其他操作系统安装包、实际 CUA 应用和第三方消息渠道仍需相应环境。 |

这些条目没有被算作“已经全部解决”。本轮以可复现的正确性和权限边界为主，没有引入新数据库、分布式队列、无限 worker、向量记忆或自动权限推断。
