## 后台任务文件恢复

普通后台任务、cron/trigger 通过同一执行器，在文件工具写入前保存原始内容，在写入后持久保存工具实际写出的内容。子代理共用任务快照，子目录内的相对路径按子代理工作目录解析。每个逻辑任务只保留一份初始快照，续跑更新写后内容，不覆盖最初版本；GBK 原始字节及文件权限仍可还原。

任务详情增加「查看文件恢复预览」→ 展示工作区、文件和冲突 →「确认恢复文件」。接口为 `GET /v1/tasks/{id}/files` 和 `POST /v1/tasks/{id}/files/restore`，没有向模型新增恢复工具。恢复执行前重新检查文件，复用桌面端已有恢复事务，不提供强制覆盖入口。

- 任务必须完全停止；同一管理器中工作区相交的其他排队/运行任务也会阻止恢复。
- 写前快照失败时拒绝修改；写后记录失败时明确报告「文件已经写入、撤销记录未完成」，不假装无副作用。
- 外部编辑冲突、损坏快照、缺少可靠写后证据的文件不盲目覆盖。可安全三方合并的文本保留外部编辑；原始字节文件按签名检查。
- 恢复开始前写入持久标记。即使中途取消或崩溃，旧任务也不能带着过时对话续跑；应新建任务。重复恢复允许重试，不移除初始快照。
- 原始字节文件的预览现在也遵守归属冲突，避免预览宣称可恢复而执行拒绝。

**覆盖边界：** 仅包括新版本执行期间、工作区内 `write_file` / `edit_file` 的记录。不追溯补建旧任务快照，不承诺撤销 Shell 任意副作用、MCP/浏览器远端操作、外部发送或工作区外写入。进程在写入完成且写后记录落盘之后退出可恢复；若恰在写入与记录之间死亡，采取保守冲突/跳过处理。快照沿用现有任务历史保留策略，没有自动清理仍可恢复的初始版本。

## 有测量支持的查询优化

发现任务列表的 `active_only` / `ids` 筛选原来发生在完整历史扫描和摘要生成之后，界面轮询因此也访问全部旧记录。

- 正在运行的调度器查询活动任务时，使用已加载的活动状态，不扫描完成历史。
- 指定 ID 的查询只检查相应文件，保留原有缓存、排序、去重和旧记录读取能力；不将 ID 当作任意路径。
- 完整历史查询保持原有行为，未引入数据库迁移或新的缓存失效机制。

真实临时 JSON 文件的合成基准，1,001 条记录，五次热调用中位数：

| 查询 | 修改前 | 修改后 |
|---|---:|---:|
| 活动任务 | 5.308ms | 0.028ms |
| 指定 10 个 ID | 5.369ms | 0.083ms |

复现脚本：`PYTHONPATH=src .venv/bin/python scripts/benchmark-task-catalog.py --records 1000`。原始数字见 `validation/task-catalog-2026-11-11.json`。这是本机合成样本，不是用户负载 P95；完整历史热查询约 5–6ms，未声称该路径获得同等提升。

## 对剩余建议的取舍

| 项目 | 结论 |
|---|---|
| 自动化额外浏览器/CUA 授权 | 继续保持默认关闭。它是新增产品能力，不是应直接放开的兼容修复；授权操作范围、会话隔离和用户专属入口尚未实现，仍留待单独设计。 |
| 旧工具/API 退役 | 保留兼容和已有使用日志。自 2026-11-11 开始计数，尚无完整 30 天零使用证据；不能现在删除。 |
| stdout/stderr 重复字段 | 保留现有工具返回契约。不能只因内容重复便删除供后续调用和展示使用的字段；未发现足够收益证明应改格式。 |
| token 估算缓存 | 沿用上一轮测量结论；现有文本缓存已生效，不增加复杂的消息缓存失效机制。 |
| 大模块拆分 | 本轮不做无行为收益的拆分；以独立变更和明确依赖边界再推进。 |
| 历史凭据 | 上轮已实现启动迁移及加密备份；未另外扫描或清理用户真实目录，保留读时脱敏兼容。 |
| 跨平台安装与其他渠道 | Windows/Linux 安装运行、Linux CUA 和其他真实渠道仍未验收。本轮没有追加外部消息或付费模型调用。上一轮 macOS TextEdit 和企业微信收件确认继续有效。 |
