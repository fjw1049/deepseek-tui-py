01

模型不变，外壳可变。 同一个模型，换个系统提示、工具说明、技能和脚本， 干活的水平可以差出一大截。这层「外壳」就叫 harness。

02

它让 AI 自己改这层外壳。 不是训练模型，而是让一个「改进者」读执行记录、 改配置文件，然后真跑一遍看效果。

03

没有标准答案也能改。 靠的是「对比」：同一道题，两种外壳各跑一次， 看行为差在哪，再把有效的部分合起来。

04

经验会攒起来。 每个领域一个经验库，后来的任务先读前面的教训， 避免每次从零开始。

一句话类比

模型是厨师，harness 是厨房：灶台怎么摆、菜谱写多细、有没有料理机、助手怎么分工。 厨师的厨艺（权重）没变，但换一套厨房，出菜的速度和成品可以完全不同。

01

什么是 harness（外壳）

先把这个词落地，后面全都好懂。

论文里的定义是：harness 是模型之外、让它能作为 agent 行动的那一整套系统—— 提示词、工具、记忆、技能、编排方式，等等。模型负责「想」，harness 负责「怎么想、能用什么、做完怎么检查」。

作者把它拆成八个可编辑部件。这个拆法很实用，因为它对应的是八种不同成本、不同作用范围的杠杆：

现实里的东西在这个框架里
厨师模型（权重固定，全程不训练）
厨房布局、菜谱、工具、备菜助手harness 的八个部件
「同一厨师，换厨房，出品不一样」同一模型换 harness，基准分数明显变化
「试做一小份，尝味道再定」Probe：把候选 harness 真跑一遍
「匿名试吃，只看成品」盲选：候选编号打乱，只看交付物
02

它要解决的两个真问题

为什么不能「人工调提示词」或者「用分数自动优化」？

难点一：开放世界里没有标准答案

传统自动优化需要一个「打分器」告诉你这次改得对不对。但真实工作任务（写法律备忘录、做财务报表、 整理会议材料）往往没有即时、可靠的标准答案。等你拿到分数，任务已经做完了。

更麻烦的是：如果让模型自己猜「评分标准想要什么」，它会开始讨好评分器，而不是把活干好。 所以这套框架从头到尾都在刻意屏蔽评分信息（后面会讲它怎么防泄漏）。

难点二：改出来的东西很容易「只对这一道题有用」

针对某个任务硬编码一堆事实和步骤，下一次换个任务就废了，甚至有害。 所以它把「流程性改进」和「领域知识」分开提案，并且要求经验必须能迁移—— 写成「什么情况下该做什么操作」，而不是「这次的数据是这样」。

关键取舍

它不追求「一次改到最优」，而追求「每一步都有证据、可回退、可复现」。 所以你会看到大量看起来啰嗦的校验、账本和隔离设计——那些不是官僚，是让自动改进不出事故的护栏。

03

核心方法：提案 → 试跑 → 组合

Propose–Probe–Compose，三步一个循环。

STEP 1
Propose 提案
改进者读任务、完整执行轨迹、当前 harness，提出一版修改（只写改动的文件）。
→
STEP 2
Probe 试跑
把改后的 harness 真正装上去跑同一道题，拿到一条新的执行轨迹和成品。
→
STEP 3
Compose 组合
对比「基准 vs 候选」的行为差异，把被证据支持的部分合成最终版。
→
STEP 4
Select 盲选
多个终版匿名化，只按交付物质量挑一个，交给下游。
→
STEP 5
Reflect 反思
把「哪个改动真的起了作用」写成一条可复用经验，存进领域库。

注意：每一步都不看分数。判断依据是「执行过程哪里不一样了」。

用仓库自带的 demo 举例（这个例子是真的能跑）

demo 的任务很朴素：把账本 CSV 里的金额求和。基准 harness 里有个脚本 scripts/summarize.py，写的是「只累加正数」——于是它漏掉了所有负数（支出）。

  1. Propose：改进者读轨迹，发现结果和账本对不上，提出删掉 if amount > 0 这个过滤。
  2. Probe：改后的脚本真跑一遍，输出变成 Total: 85.15（100.25 − 20.10 + 5.00）。
  3. Compose：对比两条轨迹，差异明确指向那一行过滤，于是保留这个改动。
  4. Reflect：写进经验库：「当账本同时包含借贷/正负金额时，求和不要过滤符号。」 下次遇到同类账本，后来的任务一开始就能读到这条。

整个过程没有评分器，也没有 ground truth，只有「执行结果和源材料对不对得上」。

为什么叫「对比式」改进

它不问「这版好不好」，而问「这版和基准比，哪个行为变了、变好了还是变坏了」。 前者需要分数，后者只需要两条轨迹。这是整篇论文最核心的一招。

为什么要分这么细？因为「贵」和「有效」经常是反的

形式成本什么时候划算常见坑
常驻文本每次运行都占上下文，还要和模型自己的输出预算抢一条对所有任务都成立的短规则越写越长，最后模型没预算干活了

这套框架的提示词里有一句很狠的话：能做成技能/脚本的，就不要写成常驻散文。 因为常驻散文是「每次都付钱」，而技能是「用到才付钱」。

05

两层递归：当场改进 + 长期攒经验

「递归」在这里不是自己调用自己，而是「改进这件事本身也被改进了」。

第一层：任务级递归（把当前这道题做好）

两种放大方式，对应两个参数 --mode：

模式怎么跑适合直觉
parallel（并行） 先跑 k 次基准，再让 k 个「流程编辑」和 k 个「领域编辑」各自提案并试跑， 最后用同一批证据组合出 k 个终版 想「广撒网」，一次看多个方向 同时开 k 口锅试菜
sequential（串行） 跑 k 轮：每轮在上一轮定稿的 harness 上再改一版，证据一路累积 想「往深里磨」 同一口锅，一轮轮调味

两种模式共享同一批基准执行——所以「基准长什么样」这个参照系是一致的，比较才有意义。

第二层：harnessing 级递归（让下次更聪明）

每个任务结束后，反思阶段会产出两样东西：

  • 一份「每个改动到底起了什么作用」的表格，判定只有四种： helped（有用）、hurt（有害）、 no observed effect（没看出效果）、confounded（混杂，说不清）。
  • 至多一条可迁移经验，格式固定为 cue / lesson / evidence / confidence——什么情况下、做什么操作、凭什么这么说、有多确信。

这些条目按「领域」存进经验库：每个领域一个目录，只装同领域的条目，任务按顺序执行、只能读更早的条目。 这样「检索」不需要向量库——目录结构本身就是检索。

一个很克制的设计

反思提示里明确说：如果证据只支持「混杂」，就写 confounded； 如果实在没有可复用的执行对比，就写 NO_ENTRY 交白卷。 宁可这条经验不写，也不许编一个归因——因为一条假经验会污染之后所有任务。

读论文时容易误会的一点

论文说「更新一个持续改进的 harness」。落到代码里，这一层其实是 「按领域持久化的经验库 + 固定提示包」，而不是让模型改写自己的提示词。 自动化程度没有字面上那么高，但也因此更可控。

为什么要做成恒等式

代码里有个 Ledger，每跑一次就记一笔，最后断言「正好 4k / 正好 3k，且没有重复标签」。 超出、少跑、两个阶段偷偷用了同一个 run id——都会直接报错。 成本可核对，实验才可复现，而不是日志里数一数。

小细节：k=1 时只有一个终版，没有可选的，所以跳过选择器会话，省一次调用。

07

三个「看不见但关键」的设计

这三点决定了它是实验框架，而不是一个会烧钱的玩具。

设计一：盲选——候选匿名，只看成品

多个终版会被随机编号成 A、B、C…（种子由「任务 + k + 模式」哈希而来，重跑结果一致）， 选择器看不到每个候选是用哪版 harness 跑出来的，只能打开交付物本身做判断。

更狠的是：提示里明确说「选原版 harness 的产物是完全合理且预期的结果」， 并且候选里可能就混着基准版。这样就避免了「越复杂越容易被选中」的偏见。

选择器罢工了怎么办？回退到一个「有交付物的基准版」，而不是随便挑一个——保证流程不中断，也不假装成功。

设计二：判分隔离——先选，再判，判不出来不算 0 分

  • 顺序隔离：选择提交之后才调用 benchmark 的判分器。改进过程从头到尾拿不到分数。
  • 失败语义：判分器返回空表示「没判成」，记为未评分，绝不缓存成 0 分。 否则一次网络抖动就会永久拉低平均分。
  • 泄漏绊线：上下文里只要出现 pass_rate、deterministic_eval_summary 这类判分器输出，程序直接抛异常，并在报错里写「这是泄漏，不是误报，去找那条读文件的路径」。
  • 只给文件名：某个基准的交付物目录里混着判分器输出，于是干脆只告诉改进者「产出了哪些文件」， 不给内容——并附一段说明，解释这是故意的。

设计三：校验闸门——先检查，再花钱

提案在被拿去跑 rollout 之前，必须先过一遍静态检查。任何一条不过，整份提案作废， 错误原文回灌给模型重试一次；再不过就回退基准版。检查项都很具体：

检查不通俗的后果通俗解释
常驻文本字符上限提示太长，模型没预算输出，跑一半就停说明书别写到没地方干活
技能必须有 description技能被加载器静默丢弃抽屉里的手册没贴标签，等于没有
技能必须被常驻文本点名永远不会被触发买了工具，但没告诉人它在哪
引用的脚本必须存在运行时找不到文件菜谱写「用料理机」，但料理机没买
Python 必须能编译一执行就语法错误先通电试一下，别到客人面前才炸
钩子 schema 必须匹配格式错了就静默不触发门禁装反了，看起来有，其实不拦
常驻文本不能有 Jinja 花括号模板渲染失败，任务开跑前就死别在填空题里再挖空

还有一个「自动修复」的小设计：如果技能忘了被点名，系统会在不超过字符上限的前提下， 自动补一行触发句——能救就救，救不了才判死。

08

证据放在磁盘上，提示只是一个指针

这条设计简单，但解决了一个大坑。

改进者每次拿到的不是一个塞满轨迹的超长提示，而是一个目录 + 一句话「去读」：

context/
  task.md                  # 任务原文（不含评分标准）
  source/                  # 任务素材
  rollouts/base1.md        # 完整执行轨迹，不截断
  deliverables/base1/      # 成品，按判分器同款方式转成文本
  harness/                 # 你正在编辑的这棵树
  library/INDEX.md         # 同领域的历史经验
  pool/                    # 候选 harness + 它的轨迹（组合/选择阶段）
MISSION.md                 # 你要做什么

好处有三个：

  • 不截断。 轨迹该多长就多长。截断会制造「假缺陷」——模型看到一个被切掉的输出， 会以为 agent 失败了，然后去修一个不存在的问题。
  • 可导航。 模型可以 grep、可以只看某一段，而不是被动接收一大坨文本。
  • 可审计。 每次调用用了哪些证据，目录原样留在磁盘上，事后能复盘。
配套的一条小规矩

交付物是用「判分器读它的同一种方式」转成文本的——比如一个没缓存计算结果的 Excel 公式， 在判分器眼里就是空单元格。所以模型看到的，就是评分时真正看到的东西。

代码地图：想读源码从哪下手

仓库约 1.27 万行 Python（不含 third_party）。真正的方法逻辑只有 core/ 那几千行。

路径干什么（人话）

core/ledger.py记账本：4k / 3k 的恒等式断言
core/spec.py「一个 benchmark 必须提供什么」的接口清单
core/prompts.py所有提示词模板（1100 多行，方法论的真正载体）
core/schedule.py任务流排序、领域并发、断点续跑
substrate/opencode.pyOpenCode 执行器：装文件、起进程、解析事件流
substrate/codex.pyCodex 执行器：同一套接口，不同的目录结构与钩子格式
benchmarks/*.py三个基准的适配器，每个约千行——所有脏活都关在这里

读源码的建议顺序

先读 core/spec.py（搞清楚边界）→ core/recursion.py（搞清楚流程）→ core/tree.py（搞清楚「一个 harness 长什么样」）→ demo.py（看一个最小闭环）。 提示词部分不用通读，挑 propose、select、experience 三段看即可。

你能从它身上抄走什么

按「投入产出比」排序，每条都给了落地方式。

01

把配置当成「可校验的树」，而不是一坨文本

八部件 = 八个路径规则 + 一组校验器。路径、上限、frontmatter 要求全是数据， 同一套逻辑同时服务 OpenCode 和 Codex。

→ 给你团队的 Claude Code / Codex 配置写一个 linter，先解决「写了但不生效」这类隐性浪费。

02

用「对比」代替「打分」来驱动改进

同一道题跑两版，比较轨迹差异，而不是等一个评分。适合任何「没有即时反馈但有可观察行为」的系统。

→ 做 A/B 提示词时，别只看最终答案，把两条执行轨迹 diff 出来看行为变化。

03

把检查放在花钱之前

静态校验能挡掉大部分「看起来对、其实不会生效」的改动：未点名技能、悬空脚本、语法错误、schema 不符。

→ 任何 agent 产出配置的流水线，都值得加一道「能加载吗 / 能编译吗 / 引用都存在吗」的闸门。

04

证据落盘，提示只做索引

不要让模型「读一大段被截断的日志」，让它自己去目录里找。截断不仅丢信息，还会制造假故障。

→ 把长上下文任务改成「工作目录 + 一段导航说明」，通常比调 prompt 更有效。

05

把预算写成断言

「4k 次执行、3k 次会话、不许重复标签」——这让「实验跑完了」变成机器可验证的事实。

→ 给批量实验加一个账本，记录每个阶段实际调用次数，和预期对不上就报错。

06

用确定性替身测试整条流水线

200 行 demo：真跑 Python、真走预算、真做选择，但不调用任何模型。测试因此便宜、稳定、可 CI。

→ 把「智能」抽成一个可替换接口，用脚本化实现覆盖调度、重试、回退、记账这些真正容易出错的地方。

如果只抄一件事

抄「校验闸门 + 证据落盘 + 盲选隔离」这三件套。 它们不是论文的创新点，却是让自动改进从「demo 很酷」变成「敢天天跑」的东西。

12

老实说，它的局限

避免把它当成开箱即用的产品。

  • 安装门槛不低。 要 Python 3.12、Node 20+、gcloud、Docker； LAB 还要 Pandoc 和 Poppler；还要克隆并给四个上游仓库打补丁。
  • 跑起来很贵。 一个任务至少 4 次真实执行 + 3 次改进会话； LAB 全量有 1143 个任务，官方建议先用 --max-tasks 1 试水。
  • 默认不限制网络。 README 自己承认：有一次 Codex 运行主动下载了它这道题的评分标准。 要拿它做评测，必须自己在网络层封掉 Hugging Face、GitHub 等出口，否则数字没有意义。
  • 研究代码的形态。 三个基准适配器各约千行，third_party/ 里全是上游补丁； 真正可复用的是 core/。
  • 经验库不是魔法。 它靠目录做检索、靠一条 cue 触发，条目多了会变吵； 论文也没有声称它能无限累积。
  • 只是「外壳」的优化。 模型本身的能力上限没变；任务太难以至于基础能力不够时，改外壳救不回来。
一句提醒

仓库是 Apache-2.0，但 third_party/ 里的基准和数据集各有各的许可证， 其中 WorkBuddy 的上游协议还带地域限制。商用前逐一看清楚。

13

小词典

读论文或源码时卡住的词，回来查这里。

Harness（外壳）
模型之外让它能干活的一整套配置：提示、工具、记忆、技能、脚本、编排。
Rollout（一次执行）
把某版 harness 装上去，完整跑一道题，产出一条轨迹和一份成品。
Probe（探针）
专门为了「看看这版改动会怎样」而跑的那次 rollout，是改进的证据来源。
Propose–Probe–Compose
提案 → 试跑 → 组合。整篇论文的方法主干。
INV / DOM
两个提案维度：INV 管「怎么干活」（流程、工具、重试、预算），DOM 管「这行懂什么」（领域规则、交付物结构）。分开是为了避免两类改动互相掩盖。
Ground truth / Rubric
标准答案 / 评分细则。这套框架刻意不让改进者看到它们。
Blind selection（盲选）
候选匿名打乱，只看成品不看来源，避免「复杂即优秀」的偏见。
Surface（可编辑面）
哪些文件允许改、改完必须满足什么规则。它是数据，不是代码分支。
Always-on（常驻）
每次运行都进上下文的文本。贵，所以只放「对所有任务都成立」的短规则。
Substrate（执行器）
真正跑 agent 的那个框架，比如 OpenCode 或 Codex。换它不该影响方法层。
Adapter（适配器）
把某个 benchmark 的任务、执行、轨迹、判分翻译成框架能懂的接口。
confounded（混杂）
一次改了好几个部件，说不清是哪个起了作用。反思阶段允许、而且鼓励诚实标注。
