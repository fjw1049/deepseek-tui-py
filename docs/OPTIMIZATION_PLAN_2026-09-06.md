# 优化方案：先修明确错误，保持现有功能与框架

日期：2026-09-06。状态：第一、二、三批已实施；暂缓项仍未实施。验收与限制见 [第一批实施记录](OPTIMIZATION_BATCH1_RESULT_2026-09-06.md) 、[第二批实施记录](OPTIMIZATION_BATCH2_RESULT_2026-09-06.md) 和 [第三批实施记录](OPTIMIZATION_BATCH3_RESULT_2026-09-06.md)。

这份方案替代上一份复核报告中的批次排序；上一份报告保留为证据清单，不代表其中所有建议都应立即实施。

目标是让现有功能按用户预期工作，减少错误目录、漏接指令、错误授权和无法停止的问题。不是重做架构，也不是把工具统一改得更保守。

## 一、总体取舍

| 安排 | 内容 | 为什么这样安排 |
|---|---|---|
| 第一批，建议实施 | 后台任务默认目录、子代理普通补充输入、审批记忆碰撞 | 已验证具体错误；收益直接；可限制在现有执行流程内修复 |
| 第二批，独立安全补丁 | 项目配置来源/LSP 执行配置、MCP SSE 跨域、审批请求冲突与结束清理 | 问题有代码或最小验证支持，但有兼容影响，需单独验收 |
| 第三批，已实施并验证 | 后台任务取消、立即打断子代理、恢复任务的权限 | 涉及运行中状态和已有副作用，不能只改一个开关 |
| 暂缓 | OS 读取白名单、auto 语义调整、全面 Shell 解析升级、大型 manager 拆分、历史自动删除 | 收益依赖实际使用场景，兼容成本较大，不应混入普通修复 |

“已验证”指此前复核中有最小复现或明确调用链，不表示每个漏洞都进行过真实网络利用。本次已重新检查第一批三个落点，缺口仍在；未重复运行上一轮整组测试。

## 二、第一批：三项明确错误，各自独立交付

### 1. 后台任务跟随当前会话目录

**现在的问题**：当前会话在项目 B，创建后台任务时未填写 workspace，任务可能采用共享任务管理器的项目 A 目录。此前使用不同的会话目录和管理器默认目录，已复现任务落到管理器目录。

**为什么修**：避免任务读错项目、找不到文件，或改到另一个项目的同名文件。让工具描述中的“默认当前工作区”真正成立。

**最小改法**：仅在模型工具新建任务的入口，缺省目录时明确填写当前 ToolContext 的工作目录，并在入队时固定。保留显式目录的现有边界检查；不改变内部自动化 API 自己选择目录的能力。

**修前 → 修后**：在 B 中创建任务、未传目录 → 现在可能去 A；修后固定去 B，即使之后切换聊天也不变。

**影响与弊端**：依赖旧的“跟随程序启动目录”行为的模型任务会改变；这是对现有工具承诺的纠正。无须新增审批，不迁移旧任务，不改 resume。

**涉及范围**：tools/task/tools.py 及任务目录集成测试。除非复现显示还需要，不改队列、调度器或持久化结构。

**验收**：
- 两个会话共用 manager，各自创建的任务都落在各自目录。
- 工作树会话使用实际执行工作树目录。
- 显式合法子目录仍可用；越界或软链接越界仍拒绝。
- 内部定时任务的显式目录行为保持；已经创建的旧任务目录不被改写。

### 2. 让运行中的子代理接收普通补充指令

**现在的问题**：send_input 返回已发送，但队列只在代理启动时读取，循环内不再读取。运行途中补充的指令可能一直留在队列里。

**为什么修**：让“补充要求、纠正方向”真正生效，减少代理继续沿着过时要求做事。

**最小改法**：保留输入队列，在下一轮模型请求前的安全边界读取新输入。按顺序加入对话，并与当前 checkpoint 规则协调，避免输入出队后遇到取消而丢失。

**修前 → 修后**：运行中发送“重点检查异常处理” → 现在下一轮可能看不到；修后下一轮带上这条要求。

**影响与弊端**：补充指令会占用少量上下文，并可能改变后续执行方向，这正是该功能的用途。它不会中断已经在执行的工具，也不能承诺立即阻止写入。界面或工具说明应明确“下一轮生效”，避免把普通补充当紧急停止。

**涉及范围**：subagent loop 的输入消费与现有 checkpoint；不重做 mailbox，不在此批实现 interrupt。

**验收**：
- 第一轮执行途中注入输入，第二次模型请求可见。
- 多条输入保持顺序、单次运行不重复注入。
- 没有新输入时原有执行行为不变。
- 在消费前后取消、恢复，输入不会因出队而静默丢失。
- 无新增输入的正常完成路径仍通过现有测试。

### 3. 防止不同命令错误复用“本会话记住”审批

**现在的问题**：审批标识把整条命令 lower 并折叠空白。已验证 `git branch -d demo` 与 `git branch -D demo` 得到相同标识；引号内大小写和空格也会丢失。

**为什么修**：批准一条普通命令，不应自动等于批准另一条强制操作。解决的是记忆授权身份错误，不是限制命令能力。

**最小改法**：用不丢失大小写、空白、参数的原始命令计算标识，并从实际执行上下文绑定工作目录。检查其他会改变本次执行效果的输入，避免仅比较显示文本。沿用现有审批缓存与审批界面，不引入新审批系统。

**修前 → 修后**：记住批准非强制删除后，强制删除可能复用 → 修后两条命令分别授权。

**影响与弊端**：等价但写法不同的命令可能多问一次；切换目录也不再复用旧授权。完全相同命令、相同执行上下文仍可复用。auto 档位不因此改为逐次审批。

**涉及范围**：tools/approval.py 及计算标识的必要调用点；不改 Shell 执行方式、不全面升级分级器。

**验收**：
- `-d/-D`、大小写不同的路径、引号内空格不产生同一授权标识。
- 相同命令在不同目录不复用授权。
- 同一上下文的完全相同命令仍可记住。
- 拒绝、单次批准、本会话批准和 auto 的既有含义保持。

## 三、第二批：三个安全边界，各自说明兼容影响

### 4. 阻止项目配置替用户选择执行程序

**现状与证据**：普通 hooks/安全档位过滤已经存在。但项目可传入 LSP server 命令；诊断启动时会使用它。cwd 配置软链接到项目外后，也可能被重新判为可信来源。已验证字段保留及软链接改变最终策略；没有把它夸大成所有 clone 都会触发。

**收益**：打开仓库和允许普通代码诊断，不应顺便授权仓库提供任意启动命令。

**最小改法**：配置的来源身份在发现时固定，解析软链接不能提升信任；项目不接受自定义 LSP 启动 argv，用户级配置仍支持。项目不能关闭用户执行策略。现有模型、语言、项目说明等普通配置能力保留。

**兼容影响**：项目自带 LSP 命令的用法需要迁移到用户配置。补丁必须给出具体被忽略字段和迁移说明，不能静默让诊断消失。不在此批新建复杂“项目信任中心”。

**验收**：普通/软链接项目配置均不能提升安全权限；项目 LSP 命令不会进入进程启动；用户配置的语言服务仍工作；普通项目配置正常生效。

### 5. 限制 MCP SSE 把认证信息转给其他网站

**现状与证据**：SSE server 返回的 endpoint 可以指向另一个 origin，后续 POST 会继续携带原 headers。已离线验证跨域地址被接受，未真实发送凭据。

**收益**：减少远程服务恶意改地址或被攻陷时，认证信息被转发的机会。

**最小改法**：对解析后的 endpoint 检查协议、主机和有效端口；默认必须同 origin，非法地址及时报错。相对路径、默认端口、`//host/path` 都要正确处理。

**兼容影响**：故意跨域部署的旧 SSE 服务可能连接失败。先检查正在使用的服务是否存在这种部署；有明确需求再设计可信显式例外。stdio、本机 MCP 和内网 MCP 不因这项补丁被统一禁止。

**验收**：同源相对地址可用；跨主机、换端口、降级协议拒绝；拒绝请求不会携带凭据发出；SSE 失败及时返回而非一直等待。

### 6. 审批请求不冲突，结束后不残留

**现状与证据**：两个请求用相同 tool_call_id 注册时，后者覆盖前者 future；已复现第一个等待不结束、第二个收到批准。结束路径也缺统一清理。看到 ID 本身不意味着能绕过 bearer 认证。

**收益**：避免同时运行多个任务时审批卡错配、等待无法结束或陈旧回答影响新请求。

**最小改法**：由服务器生成唯一审批 ID，绑定原线程/轮次/工具调用；更新事件和前端关联。取消、结束和卸载时清理对应等待；过期的旧答案明确拒绝。

**兼容影响**：事件消费者不能再把 approval_id 当作 tool_call_id。前后端必须一起验证，保留原工具调用关联字段。正常等待审批不在本批强加五分钟超时。

**验收**：两个线程相同 tool_call_id 不串审批；各自批准/拒绝只影响自己；结束后 pending 清理；旧回答不能解锁新请求；前端审批卡能正确提交。

## 四、第三批：先约定用户看到的行为

| 问题 | 建议行为 | 必须说明的代价和限制 | 动手前的验证 |
|---|---|---|---|
| 后台任务取消不及时 | 点停止后终止本次执行，等待子进程清理完成再标已停止 | 已经写入文件或发出的外部请求不能自动撤销；可能留下半成品 | 用真实但无害的阻塞子进程验证当前取消缺口及清理路径；审批中也可取消 |
| interrupt 不生效 | 区分“下一轮补充”和“停止当前生成后继续新要求” | 不能安全强停后假装工具没有执行；副作用结果不明时需先核实 | 生成中、工具执行中、工具完成未记录三个边界分别验证 |
| 旧任务恢复权限不清楚 | 默认恢复原任务身份和目录；权限高于当前会话时展示差异，由用户决定 | 一律降权可能让自动化恢复后无法工作；一律保留又可能超出当前预期 | 先区分用户主动恢复、模型请求恢复、内部自动化恢复，再测试权限处理 |

这三项不与第一批捆绑。尤其不能用“设置总取消标志”同时实现停止、打断和继续。

## 五、暂不实施的改动

- **不改变 auto=完整访问。** 当前界面已明确说明；若需要“自动批准但限制目录”，应作为单独产品能力设计。
- **不默认封禁所有内网 MCP 或所有联网。** 用户明确配置的本机服务需要继续可用。
- **不一次性收紧 OS 全盘读取。** 先列清实际需要的工具链、缓存和跨目录用法，做兼容验证。
- **不为报告重构大型 manager。** 只有具体缺陷无法局部修、且有调用链测试约束时才调整结构。
- **不自动删除历史任务。** 内存优化和历史清理不是一回事，应保留恢复与查看能力。
- **不先重做计费。** 之前确认的是 metadata fallback 算法问题，尚未证明当前主计费路径受到影响。
- **不重复实施已经完成的敏感文件、普通项目 hooks、extra_headers 等修复。** 保留其测试。

文件并发覆盖、凭据文件权限、重试一致性仍保留在复核清单中，并非判为不存在。文件覆盖如在实际使用中出现，应提前处理；凭据 0600 可做独立小补丁，但它不能替代 Shell/OS 读取边界。

## 六、怎么防止把框架改乱

1. 每一项先把已知触发场景变成能失败的测试；测试要走真实调用关系，不能只验证新 helper。
2. 每项独立变更，只触及实现该行为所需的文件。若发现必须扩大范围，先说明新证据、额外影响与替代做法，不能借机重构。
3. 验证两件事：错误场景不再错；原先正常的相邻用法仍然正常。测试通过不替代必要的界面或实际进程验证。
4. 第一批不迁移存储格式、不删除数据，便于独立回退；后续若改变事件字段，则前后端协调交付并明确兼容范围。
5. 每次交付用一句使用场景说明变化，列出实际修改范围、测试结果和仍有的限制。未完成的功能不在发布说明中写成“已修”。

**当前实施进度：第一、二批已按用户授权完成。** 第三批仍需先明确行为；暂缓项保持暂缓，不随本次扩大实施范围。
