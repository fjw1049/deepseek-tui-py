01一句话总览：三层世界观

整套机制围绕一个朴素的目标：AI 在一个隔离副本里干活，干完经过「安全的合并事务」把成果搬回你的项目；任何一步不满意，都能按回合精确倒带。为此系统里同时存在三份「世界」：

世界位置谁在用说明
项目（Project） 你的仓库目录 你本人 + 编辑器 唯一「真身」。AI 正常情况下永远不直接碰它，只在回合结束的发布瞬间经事务写入。
隔离副本（Isolate / Worktree） ~/.deepseek/worktrees/<仓库>-<哈希>/<线程ID> AI 工具 真正的 git worktree（detached checkout）。每个会话线程独享一个，AI 的所有读写都发生在这里。
检查点（Checkpoint） ~/.deepseek/threads/checkpoints/<turn_id>.json 回滚系统 每个回合一份「快照账本」：回合开始前每个文件长什么样、结束时变成了什么样。它是回滚能力的根基。

把这三个概念记住，后面所有流程都是它们之间的搬运：

     你的项目 (Project)                 AI 隔离副本 (Worktree)              回合账本 (Checkpoint)
  ┌────────────────────┐   回合开始: 复制过去   ┌────────────────────┐   回合结束: 捕获快照   ┌──────────────┐
  │   你的真实仓库      │ ───────────────────▶ │  ~/.deepseek/      │ ───────────────────▶ │ turn_id.json │
  │  (唯一真身)         │ ◀─────────────────── │  worktrees/...     │                      │ + raw sidecar│
  └────────────────────┘   回合结束: 发布事务   └────────────────────┘                      └──────────────┘
                                  (三路合并 + 全有全无)              ↑ 回滚 = 按账本把项目文件倒带回回合开始前
✓ 为什么值得这样设计

AI 跑测试可能生成临时文件、改坏配置、甚至执行 rm。隔离副本让这些破坏被限制在 ~/.deepseek/worktrees 里；发布端的三路合并又保证「你自己刚改过的文件」不会被 AI 的旧版本悄悄盖掉。两层保护缺一不可。

02磁盘上到底有什么（目录布局）

2.1 Worktree 的命名规则

每个线程的副本路径由 planned_worktree_path() 决定（src/deepseek_tui/workspace/managed_worktree.py:168）：

~/.deepseek/worktrees/<仓库名>-<SHA256前8位>/<线程ID>
                      └──── repo_slug() ────┘   └─ _safe_segment(thread_id) ─┘
  • repo_slug()（managed_worktree.py:161）：用仓库目录名 + 绝对路径哈希的前 8 位，保证同名仓库不混淆，也允许同名仓库放在不同位置。
  • _safe_segment()（managed_worktree.py:2459）：把线程 ID 清洗成只含字母数字、-_. 的安全目录名，最长 80 字符。

2.2 检查点与基线的存放位置

文件路径内容
回合检查点~/.deepseek/threads/checkpoints/<turn_id>.json回合前后每个文件的文本内容、权限位、签名、改动路径清单（turn_checkpoints.py）
不透明映像 sidecar~/.deepseek/threads/checkpoints/<turn_id>.raw/二进制、符号链接等无法放进 JSON 的文件字节本体
Worktree 基线~/.deepseek/threads/worktree_baselines/<thread_id>线程最近一次「从项目完整同步过来」的状态指纹（server/threads/store.py:47），含 head + 每个路径的内容签名；恢复决策快照 recovery_snapshot 也存在这里
ℹ 什么是「签名（signature）」

_path_signature()（managed_worktree.py:1926）对每个路径算一个字符串：类型:权限位:内容SHA256，例如 file:100644:3f2a…。符号链接取链接目标、目录记类型、不存在的文件是 missing。全文比对太贵，签名比对等价且快——它是整个系统判断「这个文件到底变没变」的通用货币。

03Worktree 的一生：创建 → 同步 → 发布 → 回收

生命周期由两层协作完成：workspace/managed_worktree.py（约 2500 行）提供全部无状态原子原语；server/threads/manager.py（约 6600 行）作为回合编排者，在正确的时机调用它们并持久化基线与日志。下面按时间顺序走一遍。

STEP 1创建回合开始时若无副本则新建 detached checkout
STEP 2同步把项目当前状态（含未提交改动）镜像进副本
STEP 3干活AI 工具全部工作在副本目录里
STEP 4发布回合结束，检查点影像三路合并回项目
STEP 5回收空闲 3 天且干净的副本被删除

3.1 创建：create_managed_worktree()

managed_worktree.py:185。编排者 _prepare_isolated_workspace()（manager.py:1168）在每个回合开始、会话恢复（resume）、预热时调用它。步骤：

  1. 校验：目标必须是 git 仓库且有 HEAD 提交，否则抛 WorktreeError。
  2. 占用检查：目标路径已存在时，若里面有未发布的成果（worktree_has_labor()）就拒绝覆盖直接报错；只有干净副本才会被移除重建。
  3. 建树：git worktree add --detach <路径> <HEAD> —— 用 detached checkout（不占分支名），基线就是当前项目的 HEAD。
  4. 复制脏状态（copy_tracked_dirty=True 时）：
    • 已跟踪文件的未提交改动：git diff --binary HEAD 生成补丁，在副本里 git apply --binary（managed_worktree.py:1797）——二进制安全。
    • 未跟踪文件：逐个 _copy_raw() 原样复制（保留符号链接身份，managed_worktree.py:1822）。
    • .worktreeinclude 指定的「故意被 gitignore 的环境文件」（如本地 .env、配置）也会复制（managed_worktree.py:1839），让 AI 在副本里能跑起同样的开发环境。
ℹ 为什么要复制未提交改动

你常常写到一半就丢任务给 AI（比如让它「帮我跑测试」）。如果不复制 node_modules 之外的未提交文件，AI 在副本里看到的是另一个世界，测试结论就不可信。复制让副本成为项目的完整镜像，而不是某个历史提交的快照。

3.2 同步：sync_isolate_from_project()

managed_worktree.py:564。每次回合开始都执行，目的是让副本和项目此刻完全一致——包括副本创建之后你在项目里新做的提交和修改。这是整套系统里防御最严密的一段：

  1. 劳动清点：用基线（WorktreeBaseline）区分副本里的文件是「项目同步来的」还是「AI 上回合的劳动」。有未发布劳动且与项目不一致时，抛 UnpublishedWorktreeError（→ 触发第 5 节的恢复横幅），绝不静默丢弃。
  2. 分支保护（manager.py 同步封装处）：若副本被 promote_worktree_branch() 升级成了用户命名的分支，同步直接返回不动它——用户命名的分支是持久性承诺，不静默移动。只有 ds/ 前缀的遗留内部分支才参与自动管理（_is_legacy_internal_branch()，managed_worktree.py:2245）。
  3. 提交保护：若副本 HEAD 上有尚未进入项目分支的提交（merge-base --is-ancestor 判定不可达），同步返回、保留这些提交。
  4. 执行同步（在 before_mutation 日志保护下）： 
    git checkout --detach --force <项目HEAD>   # 先把副本的 git 状态对齐项目提交
overlay_working_paths(项目 → 副本)         # 再把所有差异路径的字节逐个覆盖过去
    覆盖前先写入 journal（before/target/target_head/checkout_target_head 四组签名，manager.py:1163 附近调用 before_mutation）——如果同步中途崩溃，重启后系统能靠 journal 判断「这些字节是同步写到一半的产物」，而不是误判成 AI 的劳动。
  5. 收尾校验：同步完成后重新捕获基线，与目标基线比对；不一致说明同步期间有人动了文件，抛错重来。

3.3 干活：工具被「圈」在副本里

workspace/execution.py 只做一件事：回答「工具应该在哪个目录工作」。worktree 模式下返回 execution_root（即副本路径）；副本还没准备好时抛 WorktreePendingError，上游会等待重试。另外两道护栏：

  • 项目租约（workspace/project_lease.py）：跨进程文件锁（flock）。同一时刻只允许一个线程对同一个项目执行发布/恢复等写操作，多窗口互不踩踏。
  • Shell 写保护（workspace/shell_write_guard.py）：审查 AI 发出的 shell 命令，阻止它改写允许目录之外的源码文件。允许写入的只有 scratch/、tmp/、node_modules/、dist/ 等白名单前缀和日志类后缀（shell_write_guard.py:10-40）。

3.4 回收：三种途径，全部「宁留勿删」

途径触发时机安全条件
reclaim_managed_worktree()
managed_worktree.py:1741		 回合边界定期清理（manager.py:2229 reclaim_idle_worktrees()，空闲超过 IDLE_WORKTREE_RECLAIM_AFTER = 3 天，manager.py:144） 只删 owned + 路径合法 + 无任何劳动 的副本；返回四态 removed / kept / skipped / gone。清理前最后再查一次干净状态，绝不 --force。
prune_orphaned_worktrees()
managed_worktree.py:849		 启动、清理线程等时机（manager.py:2224） 只回收不被任何线程引用的孤儿副本；不属于管理目录、不是 git worktree、有脏文件、有不可达 detached 提交的一律留下。
删除会话时的 delete_thread_tree() 用户在侧边栏删除会话 见第 7 节：脏副本会先弹「未同步代码将被永久丢弃」的二次确认（i18n key sidebarDeleteUnpublishedConfirm）。
⚠ 「劳动」的判定比你想象的宽

_has_labor_sync()（managed_worktree.py:2092）认为以下任一情况都算有劳动、不许删：git status 非空；.worktreeinclude 文件存在（宁滥勿缺）；甚至 detached HEAD 不可达（_detached_head_is_unreachable_sync()，managed_worktree.py:2161）——即当前检出没有任何分支/标签引用保护，删了目录提交就真丢了。宁可多留几个空目录，也绝不冒丢代码的险。

04发布事务：为什么你的文件永远不会被写坏

回合结束时，编排者调用 _publish_isolated_thread()（manager.py:1372）把本回合 AI 改过的文件搬回项目。这是全文最核心的一段，它是一条多阶段事务：

1取检查点读出本回合 mutated 路径的 base（回合前）/ theirs（回合后）影像
2规划对每个路径做三路合并判定，任何冲突则整体不写
3记账写前先把影像重定向到项目（retarget_to_project），日志落盘
4写入逐路径原子写，写入前后都校验签名
5收尾全部成功→标记 checkpoint 已消费；任何失败→整批回滚

4.1 三路合并怎么判（_plan_path()，managed_worktree.py:1773）

每个文件涉及三个版本：base（回合开始前）、ours(项目此刻)、theirs(AI 回合结束)。判定顺序：

情况结果
ours == theirs（AI 改完又变回了原样 / 项目已是目标态）applied 无操作，视为成功
强制模式（overwrite / force / 用户选「使用本次对话版本」）applied 直接采用 AI 版本
ours == base（回合期间你没动过它）applied 安全采用 AI 版本
theirs == base（AI 没动过它）applied 保留项目版本
两边都改了但改的是不同区域merged 三路文本合并（_merge3）成功
两边都改且合并不了conflicted 挂起等用户决定

4.2 文本路径的事务：apply_path_images()

managed_worktree.py:1012。要点逐条：

  • 全有全无：规划阶段出现任何 conflict/skip 且未强制 → 一个字节都不写，报告清空返回。用户看到的是「这次发布整体没发生」，而不是写了一半的混合状态。
  • 写前记账：before_write 回调（即 manager.py 的 stage_publish → checkpoints.retarget_to_project()）在第一个字节写入项目之前把检查点日志固化——即使进程在写一半时被杀死，重启后日志也能指导恢复。
  • 双签名校验：写每个文件前后都比对 _path_signature。写前发现项目文件变了（比如你的编辑器刚保存）→ 立刻中止并回滚；写后验证落盘内容确实等于预期。
  • 失败即回滚：按写入的逆序把每个文件恢复为写入前的 pre-image；回滚时如果发现文件又被第三方改了，跳过该文件不覆盖（「绝不滚回盖掉别人刚写的字节」），并在报告中如实标注。
  • 产出 post_signatures：全部成功后记录每个文件「写入后的签名」，后续回滚用它与当前磁盘状态做 CAS（compare-and-swap）比对，保证只回滚「确实是我们写的状态」。

4.3 不透明路径的事务：apply_raw_path_images()

二进制文件、符号链接、超大文件（>512KB）不能走文本合并。它们有独立的事务通道（managed_worktree.py:1199）：

  • 检查点为它们保存 pre/post 两张「原始映像」：kind（missing/file/symlink）+ 权限位 + 内容 SHA256，字节本体在 .raw/ sidecar 里，写入前会重新校验 sidecar 哈希（_raw_image_is_valid()）。
  • 写入时要求目标当前必须等于 pre 或 post 之一：等于 post → 幂等跳过；等于 pre → 覆盖；两者都不是（「第三态」，比如你刚手动改了这个二进制）→ 拒绝写入，报 conflicted。
  • 失败时按逆序把已写的路径翻回对面映像；中途崩溃则下次重放同一调用自动补完（幂等）。
✓ 文本与原始两条通道被编排者绑成一个事务

manager.py:1686 附近：若文本路径全部写成功、随后 raw 路径失败，编排者会用文本报告里的 post_signatures 构造反向影像（base=post, theirs=pre）调用 apply_path_images 把文本部分也滚回去——保证「一次发布」在磁盘上要么完整发生，要么整体没发生。

4.4 发布成功后

  • checkpoints.mark_publish_applied() 把检查点标记为已消费；已发布路径不再是「未发布劳动」。
  • 副本被再次同步到项目最新状态（含刚发布的改动），基线前移——下个回合从干净一致的状态开始。
  • 检查点文件保留在磁盘（不删除），因为「回滚到这个回合之前」的能力还需要它；只有被回滚消费后才删除。

05冲突与恢复：横幅上的五个状态

发布并非总是一帆风顺。线程记录上有一个 publish_issue 字段（manager.py:149-155），前端据此渲染 PublishConflictBanner。状态机在 publish-conflict-state.ts：

publishAttentionState(rawConflicts, publishBlocked, publishIssue)
  → hidden | recovery | failure | missing | conflict
状态含义触发原因横幅文案（zh）用户可选动作
hidden 一切正常无阻塞、无冲突不显示横幅（可能只有状态提示：「正在同步…」「本次对话的修改已同步到项目文件夹」）—
conflict 文件级冲突发布时某些路径两边都改过且无法合并「项目中的 N 个文件也被修改过」
publishConflictTitle		 保留项目版本（keep_project）｜使用本次对话版本（use_agent）｜查看冲突
recovery 未发布劳动待裁决副本里存在没有检查点背书的改动（UnpublishedWorktreeError），或发布/恢复链路中断后的残留「发现两份不同的文件版本…两边都还在，没有内容被覆盖」
publishRecoveryTitle		 保留项目版本｜使用这次任务版本｜取消（选择需与 recovery_token 快照匹配，防止「看的是旧状态、删的是新字节」）
failure 发布失败写盘/合并流程出错（PUBLISH_FAILED）「修改未能自动同步…修改仍安全保存在当前任务中」
publishSyncFailedTitle		 重试同步
missing 工作区丢失副本目录不见了（被手动删除等，WorktreePendingError）「找不到这次任务的工作区…为保护文件，已停止同步，项目不会被覆盖」
publishMissingTitle		 重新检查工作区

5.1 用户的每个决定如何被执行

横幅按钮 → POST /v1/threads/{id}/worktree/resolve（routes.py:1353），请求体 ResolvePublishRequest（models.py:233）带 action / paths / recovery_token 三字段，进入 manager.request_publish_action()（manager.py:1854）：

action后端做什么后果
apply 正常发布一次（_publish_isolated_thread），可带 force_paths 或 keep_project 路径清单 按第 4 节事务走一遍；冲突路径按清单强制采用 AI 版或保留项目版
use_agent 对指定路径走 resolve_unpublished_worktree_labor(use_worktree=True)（managed_worktree.py:1645）：把副本字节原子 raw 拷贝到项目（apply_raw_paths，先做源签名绑定+备份），然后重新同步副本、前移基线 项目指定文件 = 副本版本；拷贝失败会整批还原
keep_project use_worktree=False：方向反过来，把项目字节拷回副本覆盖 副本里的这些改动被放弃；项目不动
⛔ 不会发生的事

无论哪个状态，后端都不存在「把项目文件静默覆盖」的路径：文本冲突挂起等选择、二进制第三态拒写、recovery 选择绑快照令牌、横幅上明确告诉你「两边都还在，没有内容被覆盖」——这些都是同一原则的不同侧面。

06回滚（Rewind / 恢复代码）：完整链路

回滚回答的是另一个问题：「前面几个回合 AI 改的东西，我不想要了，把文件和对话倒回去。」它和发布（第 4 节）是两条独立链路，但共享同一批检查点。

6.1 检查点里有什么

每个回合一份 TurnCheckpoint（turn_checkpoints.py:128-232），关键字段：

字段含义
pre_contents / post_contents回合开始前 / 结束时每个改动路径的完整文本；None 表示当时不存在（恢复 = 删除该文件）
pre_modes / post_modes对应的权限位，恢复时连 chmod 一起还原
raw_pre_images / raw_post_images二进制/符号链接的原始映像描述符，字节在 .raw/ sidecar
mutated本回合 AI 确认改动过的路径（有序）
uncertain回合末由 git 状态推断「可能是它改的」路径——所有权是猜测，恢复时按不确定处理，绝不与第三方修改合并
head / execution_root回合开始的项目 HEAD；捕获时的执行根（发布成功后重定向为项目根）
publish_pending_sync / publish_apply_complete发布两阶段日志标志，崩溃后据此续跑

6.2 三个 HTTP 端点（前端 → 后端）

端点定义作用

6.3 一次「还原代码并重发」的完整时序

前端 MessageTimeline（用户点消息菜单「回到此处」）
  ├─ 1. provider.rewindPreview(threadId, itemId)      → GET /rewind-preview
  │     rewindPreviewNeedsConfirmation() 判断是否需要弹窗（有文件影响就弹）
  ├─ 2. 弹出 rewind-resend-confirm 确认框：
  │     · 仅回退对话并重发        → restore_files=false
  │     · 还原代码并重发          → restore_files=true
  │     · 「同时覆盖冲突文件」     → force_conflicts=true（勾选才传）
  └─ 3. provider.rewindThread(...)                    → POST /rewind

后端 _rewind_thread_with_result（manager.py:3086）—— 全程在一个临界区内：
  ├─ 校验：该线程当前没有活跃回合（否则 400 "cannot rewind thread while a turn is active"）
  ├─ 加锁：线程操作锁 + 项目租约（restore_files 时）+ _active_lock
  │        （start_turn 抢的是同一把锁 → 回滚绝不会和新回合的写入交错）
  ├─ 选检查点 _checkpoint_candidates()（manager.py:2942）：
  │     被删回合的 checkpoint + 本线程的「孤儿 checkpoint」（更早对话级回滚遗留）
  │     按创建时间新→旧排序；早于截断点的孤儿绝不重放（保守）
  ├─ restore_files=true 时：
  │     checkpoints.restore() 把每个文件写回回合开始前的状态
  │     · 第三方改过的路径 → 合并或标 conflicted（force 才覆盖）
  │     · 不可恢复的 → skipped；结果分四类返回 restored/merged/conflicted/skipped
  │     · 有未解决路径的 checkpoint 保留为孤儿（还能再次 restore-code / 强制恢复）
  ├─ _resync_isolate_after_project_restore()：项目回滚后把干净副本重新对齐；
  │     副本此时若有脏文件 → 置 publish_pending + recovery 横幅（绝不覆盖）
  ├─ 消费：全部成功的 checkpoint 从磁盘删除（幂等重放不再发生）
  ├─ 截断对话：删除 before_item_id 及之后所有 item/turn，重算 latest_turn_id
  └─ 重建引擎会话：warm engine 不再看到被删历史；广播 thread.rewound 事件

6.4 restore_code 与 rewind 的分工

rewind（编辑并重发）restore-code（恢复代码）
对话截断到目标消息之前不动
文件可选还原（弹窗让用户选）必还原
典型入口消息悬停「编辑」→「重新发送」「回到此处」的纯代码恢复路径
checkpoint 处理restore_files=false 时保留为孤儿（只回对话不删证据），之后仍可 restore-code成功后消费删除
ℹ 剪切点语义（v1）

两个接口都以「回合（turn）」为最小剪切单位：即使 before_item_id 位于回合中间，该回合整体被还原/消费。UI 只在用户消息（必是回合第一条）上暴露回退入口，所以当前语义没有歧义；未来若开放回合内截断，需先解决这个语义问题（manager.py:3116 注释原文）。

6.5 与 TUI 内置机制的区分（容易混淆）

  • Workbench 的 rewind / restore-code —— 本节主角，基于持久化检查点，重启后依然可用，字节级精确。
  • TUI 的 /undo（tui/commands.py:2027）—— 另一套弱机制：只撤销最近一次改文件的工具调用，基于内存快照，不等于回合回滚。两者不要混为一谈。
  • TUI 的 Esc-Esc backtrack 状态机 —— 目前只接线到选择状态（confirm/step 无调用方），真正可用的回滚 UI 在 Workbench 前端。

09常见疑问 FAQ

Q1：AI 说「已修改文件」，我的项目目录里为什么看不到？

改动先落在 ~/.deepseek/worktrees/<仓库>/<线程>。回合结束发布成功（横幅短暂显示「本次对话的修改已同步到项目文件夹」）后才会出现在你的项目里。若横幅显示「正在等待另一个任务完成」，说明另一个会话正持有项目租约，会自动排队。

Q2：发布冲突时选「使用本次对话版本」，会丢掉我自己的修改吗？

被选中的那几个文件会（这正是选项的字面含义），但只作用于冲突清单里的文件——横幅文案明确「你的选择只作用于这些冲突文件，其余修改仍会正常同步」。选择前可以点「查看冲突」逐个看差异。

Q3：只回退了对话没还原代码，之后还能还原吗？

能。那时检查点被保留为「孤儿」且有意不清理（无 TTL），随时可用 restore-code（或再次 rewind 勾选还原代码）把文件回滚。代价是磁盘占用——这是「空间换可回滚性」的明确取舍（manager.py:3110 注释）。

Q4：为什么有的回合「没有可用的代码还原记录」？

检查点只可靠记录文本文件；二进制/符号链接有 raw sidecar，但极旧版本、捕获失败或超大文件的路径可能没被记录。这类回合对话仍可回退，文件部分会如实标注「不可恢复」（rewindResendConfirmNoCheckpoint）。

Q5：~/.deepseek/worktrees 里有一堆目录，能手动删吗？

可以，但建议先让系统自清理：空闲 3 天的干净副本会被自动回收。手动删除一个「有未发布劳动」的副本，会触发该线程的 missing 横幅（工作区丢失）——系统不会因此覆盖项目，但那个会话的未同步改动就真没了。

Q6：回滚会不会把回滚之后我自己改的文件覆盖掉？

不会。restore 时对每个路径都检查「它现在是否还是回合结束时的样子」：被你改过的路径要么三路合并、要么标记冲突保持原样，默认绝不覆盖；只有显式勾选「同时覆盖冲突文件（会丢弃他人的改动）」才会强制。

Q7：两个会话同时给一个项目改代码会怎样？

各自有独立副本互不干扰；发布端靠项目租约串行化——后完成的会话发布时，会看到先完成会话写入的字节（作为新的 ours 参与三路合并），冲突才挂起，不冲突直接合入。
