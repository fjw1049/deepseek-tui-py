DeepSeek TUI · Workbench 优化说明

Git 管理不及时 + 编辑重发覆盖他人改动 —— 问题排查与通用解决方案

这份说明按对话的完整逻辑，把「用户反馈 → 排查代码 → 定位根因 → 设计通用方案 → 分层落地 → 测试验证 → 提交分支」 全过程讲清楚，尽量不遗漏细节，但用尽量通俗的语言表达，图表和代码片段辅助理解。

分支：build_0805 → build_0806 改动文件：24 个 新增测试：8 + 1 个用例 后端测试：1507 通过 前端测试：466 通过

01问题背景

用户最初提出的两个现象，以及为什么说第二个问题"很致命"。

现象一 Git 状态显示不及时

Workbench 里的分支徽章、改动文件列表，经常和磁盘上的真实状态对不上，需要手动点一下才会刷新，体验上感觉"迟钝"。

现象二 编辑重发会吞掉别人的改动

在一个会话里编辑并重新发送消息、选择"还原代码"后，会把其他会话或者外部编辑器（Cursor / Claude 等）同一时间段对同一文件做的修改也一起抹掉——这是数据丢失级别的问题。

🎯 用户的诉求

不只是"修个 bug"，而是要求从通用兼容性的角度分析：改动来源多种多样——不同编辑器（Cursor / Claude Code / 命令行）、 同一编辑器里的不同会话各自在做不同功能——现有设计在这种"多主体同时改同一份代码"的场景下有什么系统性缺陷， 并给出一个通用的、可长期依赖的解决方案，而不是打补丁。

02排查过程

先把两条链路的代码完整读一遍，再下结论——这是避免"猜问题"的关键一步。

2.1 后端：编辑重发 / 回滚（rewind）链路

核心文件是 turn_checkpoints.py：每一个"回合"（turn，即用户一句话 → AI 一次响应的完整过程）开始时， 系统会给它建一个 JSON 快照文件，记录这个回合改动了哪些文件、改之前长什么样。用户点"编辑重发 + 还原代码"时， 系统就把这些文件"改之前的样子"重新写回磁盘。

2.2 前端：Git 状态显示链路

Workbench（Electron 应用）里，git 分支徽章、改动文件列表并不是靠"定时轮询"或者"文件系统监听"来刷新的， 而是完全依赖 AI 助手自己的操作事件驱动：

  • AI 写完文件、执行完 shell 命令 → 触发一个内部计数器 workspaceDirtyTick +1；
  • 各个面板订阅这个计数器，防抖 500ms 后重新去问一次 git 状态；
  • 但 外部编辑器（Cursor / VS Code）改文件、或者用户手动保存，压根不会触发这个计数器 —— 所以显示"迟钝"；
  • 而且每次刷新都要跑一次完整的 git diff HEAD，仓库大的话本身就要好几秒；
  • 还有几个小组件（比如分支选择器）压根没订阅这个刷新机制，永远不会自动更新。
⚠️ 排查小结

两个问题表面不相关，但根子上是同一件事：系统假设"文件只会被当前这一个 AI 会话改动"。 这个假设在单会话、单编辑器场景下没问题，但只要引入"多会话并行"或"外部编辑器同时在用"，就会暴露出两类症状—— 一类是"看不到别人的改动"（显示不及时），一类是"看不到就顺手抹掉"（覆盖冲突）。

03根因拆解：为什么"还原代码"会吞掉别人的改动

拆成三个具体成因，每一个都有对应的代码位置和后果。

成因一：恢复的"单位"错了

旧逻辑还原的是"文件在回合开始时的完整快照"，而正确的语义应该是"撤销这个回合自己引入的那部分变更"。 文件是所有会话共享的资源，"写回整份快照"等于宣称"这份文件从回合开始到现在的一切变化都是我的" —— 这个假设在多主体场景下必然不成立。

成因二：没有做冲突检测的"原材料"

旧的 checkpoint 只存了"改动前"的内容（pre-image），没有存"回合结束时"的内容（post-image）。 没有 post-image，就没法回答"现在磁盘上的内容，还是不是这个回合刚结束时的样子"——也就完全没有能力判断"这段时间是否有第三方插手过"。

成因三：turn 结束时的"账"算错了归属

每个回合结束时，系统会跑一次 git 对账（reconcile），把"这个回合期间新出现、还没被记录过的脏文件"统统算成这个回合改的。 如果两个会话同时在跑，或者你在 Cursor 里同时手动改了文件，别人的改动会被错误地记进你这个回合的 checkpoint。 更糟的是：这类文件往往没有 pre-image，还原时会退回去查 git show HEAD:path——如果那个文件是"别人刚创建的新文件"， HEAD 里根本没有它，还原逻辑会直接把它删掉。

🔥 一个具体的翻车场景
A
会话 A 打开一个回合，把 utils.py 从 "old" 改成 "new"。
B
与此同时，你在 Cursor 里手动把同一个文件改成了 "final"（这是你真正想保留的版本）。
C
你对会话 A 做"编辑重发 + 还原代码"——文件被直接写回 "old"，你在 Cursor 里的 "final" 改动凭空消失，没有任何提示。

04通用方案思路：参考业界成熟做法

这一步是为了避免"闭门造车"——先看看别人是怎么解决这个通用问题的。

业界处理"AI 编码助手回滚代码"这个问题，主要有两条路子：

方案代表核心思路优点代价
Shadow Git Cline / Cursor 的 checkpoint 为工作区建一个"影子仓库"，每回合结束自动 commit 一次，回滚 = 对该 commit 做 revert 三路合并、冲突标记、二进制文件、重命名全部交给 git 处理，不用自己造轮子 需要维护一个嵌套 git 仓库，索引/锁隔离、大仓库性能是工程坑
变更流回放 JetBrains Local History 记录每一次"变更"而不是"快照"，回退时按变更粒度回放 天然支持"只撤销我这部分" 需要自己实现差异存储和回放引擎
✅ 两条路子的共同点，也是本方案的核心原则

恢复的单位是"变更"（diff），不是"快照"（全文）；恢复前必须做冲突检测。 我们选择在现有 checkpoint 机制上做增量改造（而不是引入嵌套 git 仓库）， 用最小的改动实现和 shadow git 语义等价的效果：只需要再多存一份"回合结束时"的内容（post-image）， 三个时间点（改动前 / 改动后 / 现在）放在一起比较，就能做出等价于 git 三路合并的判断。

三层实施顺序

按照"先止血、再补根、后提验"的顺序分三层落地：

层级解决什么关键改动
第一层覆盖他人改动（核心问题）post-image + 三路合并 + 冲突报告，替换掉"无条件覆盖写回"
第二层归属算错、盲删文件turn 结束对账时排除别的会话已认领的路径；无 post-image 的路径不再允许删除/回退
第三层显示不及时（体验）原生文件系统监听 + 防抖上限 + 结果缓存 + 补齐订阅

05第一层：冲突感知式回滚（核心）

这是整个方案里分量最重的一层，直接解决"覆盖他人改动"的问题。

新增一份"回合结束时的快照"（post-image）

每个回合结束时（也就是 AI 这一轮响应完全结束的那一刻），系统现在会把这个回合改过的每一个文件， 再拍一张"结束时长什么样"的快照，存进 checkpoint 里的 post_contents 字段。 这样每个被改过的文件，checkpoint 里就同时有了"改之前"和"改之后"两个参照点。

还原时，从"无条件覆盖"变成"三分支判断"

现在还原一个文件时，会先把"当前磁盘上的内容"和这两个参照点做比较，走三条不同的路：

条件
✅ 当前内容 = 回合结束时的内容
说明这段时间没有第三方碰过这个文件——安全，直接写回"改之前"的内容。这是最常见的情况，行为和以前完全一样。
条件
🔀 当前内容 ≠ 结束时内容，但能三路合并
说明有人在这之后又改了文件，但改的是不同的地方——用 git merge-file 做三路合并（基准=回合结束时的内容，一方=当前内容，另一方=改之前的内容）， 效果是"只撤销这个回合改的那几行，别人后来加的内容原样保留"。
条件
🚫 合并不了 / 没法证明归属
改到了同一行，或者压根没有 post-image 可比对——这个文件整个跳过，原样不动，并在报告里标为"冲突"，用户可以手动选择是否强制覆盖。
🛡️ 一条铁律：无法证明归属，就绝不删除/覆盖

之前那种"归因不确定的文件，退回去查 git 历史，查不到就当成新建文件直接删掉"的做法被彻底禁止了。 现在只要拿不出这个回合"结束时长什么样"的证据，一律判定为冲突、原样保留，把决定权交还给用户。

预览功能：不动手也能提前看到结果

新增了一个"预览"能力（对应"编辑重发"时弹出的确认框）：在真正执行还原之前，先按同样的三分支逻辑跑一遍， 但不实际写磁盘，只是把每个文件的预计结果（安全还原 / 合并 / 冲突）报告出来，用户看得明明白白再决定要不要继续。

接口层面的变化

  • POST /rewind、POST /restore-code 新增 force_conflicts 开关——默认关闭（保守），用户主动勾选后才会强制覆盖冲突文件；
  • GET /rewind-preview 返回值从"文件列表"升级为"每个文件的预计状态"（还原成功 / 已合并 / 有冲突 / 无法处理）；
  • 有冲突的 checkpoint 不会被消费掉，会保留下来，之后还可以用"强制模式"重新尝试还原。

06第二层：归因围栏（防止算错账）

堵住"回合结束对账"环节里把别人的改动记到自己头上的漏洞。

排除其他会话正在处理的文件

每个回合结束做 git 对账时，现在会先看一眼：同一个工作区里，还有没有别的会话正在跑、并且已经声明过要改某些文件—— 如果有，这些路径会被排除在外，不会被这个回合"顺手"认领走。原则是宁可漏记（少了一次可回滚的机会），也不能错记（把别人的东西划到自己名下）。

"猜测归属"的文件要求更严格

通过对账猜出来的改动（而不是工具/shell 明确记录的），会打上一个"不确定"标记。 还原这类文件时，标准会提高到"必须和回合结束时的内容完全一致才允许动"——连三路合并都不做， 只要有一丝出入就直接判定冲突，因为这类归属本身就是猜的，不能在猜测的基础上再做自动合并。

💡 为什么要分两种严格程度

工具（写文件 / shell）产生的改动，系统知道确切是哪次操作改的，可以放心做三路合并； 而"对账猜出来的"改动，本质上是"这段时间冒出来的脏文件，八成是这个回合改的"这种概率性推断， 一旦这个推断本身就错了（比如其实是别人改的），再去做智能合并只会让错误更难被发现——所以对这类文件反而要更保守。

07第三层：显示及时性（体验优化）

这一层和"覆盖冲突"没有直接关系，但解决了用户反馈的第一个现象。

加上真正的文件系统监听

以前 Workbench 完全不监听磁盘变化，只靠 AI 自己的操作事件驱动刷新。现在在 Electron 的主进程里加了一个原生的 文件系统监听服务：只要工作区里的文件发生变化——不管是 AI 改的、你在 Cursor 里改的、还是命令行里跑脚本改的—— 都会被捕捉到，防抖处理后通知界面去刷新 git 状态。

忽略 node_modules / .venv / dist 等目录 忽略 .git/index（避免 git status 自己触发死循环） 只关心 .git/HEAD 和 .git/refs（分支切换、提交）

防抖机制加了"保底上限"

以前的刷新防抖是"安静 500 毫秒后才刷新"，但如果改动一直连续不断（比如跑一次构建）， 这个 500 毫秒窗口会被不断重置，导致刷新被无限期推迟。现在加了一个 2 秒的硬上限——无论改动多频繁， 最多等 2 秒也一定会刷新一次。

减少不必要的重复查询

每次刷新原来都要重新跑一遍完整的 git diff HEAD（大仓库会比较慢）。 现在加了一层"指纹缓存"：先算一个便宜的指纹（当前 HEAD、git status 输出、每个改动文件的修改时间和大小）， 如果指纹和上次一样，就直接复用上次的结果，不用重新跑一遍昂贵的 diff。

补齐了漏掉的订阅

分支选择器（GitBranchPicker）之前只有在用户手动点开菜单时才会刷新，完全没有跟着上面的刷新机制走—— 现在也接入了同一套刷新逻辑，保证不管从哪个入口看，看到的都是最新状态。
