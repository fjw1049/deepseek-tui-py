1. 总览：这个 CUA 是什么

CUA（Computer Use Agent，电脑使用代理）让模型能够直接操控你的桌面应用——点按钮、打字、截屏、读窗口内容。本项目没有自己实现桌面操作 API，而是接入 LCU runtime（本机安装的 CUA 运行时），只做一层"宿主适配"：

  • 对模型只暴露两个工具：cua_js 和 cua_js_reset——就是 LCU 原生的 js / js_reset，参数、描述、文档全部来自运行时实时下发，本地不维护第二套 API 副本（避免两份文档漂移）。
  • 现有的 browser_use 管 Workbench 内置浏览器；CUA 管桌面应用（可选接管外部 Chrome）。两者互斥同一表面。
  • 整条链路上有 12 项安全护栏（第 8 节），核心哲学只有一句话："宁可重连重观察，绝不盲目重放一个可能已经执行过的点击"。

为什么中间要有一个 Node 子进程？LCU 客户端是 Node 模块，Python 进程无法直接 import。桥接进程是纯宿主侧的：模型代码只能到达 client.call，永远摸不到桥本身的生命周期接口。stdout 只输出分帧 JSON，stderr 被 Python 侧静默排空（运行时日志可能含桌面数据，绝不回显进聊天）。

3. 一次工具调用的完整流程（通俗版）

假设模型要打开"备忘录"并输入文字，它调用 cua_js，参数是一段 JS 代码。从上到下走一遍：

1

每轮开始：引擎准备会话（_prepare_cua）

引擎在取工具列表时检查：CUA 开了吗？计划模式吗？当前模型支持看图吗（不支持则查 vision.model 辅助路由，两者都不行就不暴露工具）？上次连接失败还在 30 秒退避期内吗？全过关才建立 CuaSession 并注册 cua_js / cua_js_reset。

2

工具执行入口：三道前置检查（CuaTool.execute）

① 有没有 reset_reason（之前被人工接管/断连过）？有就直接拒绝，提示"从文档化的入口重新观察"。② 包一层 session.run()，把"停止/暂停"事件监听挂上。③ 拿到宿主轮次 ID 和调用 ID 传入（模型无法伪造生命周期通知）。

3

会话层拿锁、建运行段（CuaSession.call）

进程内互斥 → 确保连接活着 → 获取跨进程桌面文件锁（整个轮次持有，不是单次点击）→ 生成新的运行段 ID "turn-id:cua:随机hex"，宿主轮次 ID 放进 metadata。为什么不直接用轮次 ID？因为原生 runtime 记得住已结束的 ID，接管恢复后复用会被拒。

4

JSONL 消息进桥，桥调 LCU 客户端

Python 写一行 JSON 到桥进程 stdin；桥解析后调 client.call(name, args, context)，每个调用挂一个 AbortController（后面中断用）。应答写回一行 JSON，Python 按 id 配对唤醒等待中的 Future。

5

途中可能弹出授权卡片（elicitation）

LCU 要访问"备忘录" → 原生 runtime 发起授权请求 → 桥转发给 Python → 走宿主审批 UI 弹卡片给你。你点"允许一次"才放行（详见第 7 节）。等待期间动作超时被冻结——人在考虑，不应该倒计时。

6

结果回来：转成工具结果 + 后处理

截图走现有图片管线（原始字节不重编码，标记来源 kind:"cua"）；文本超 64 KiB 就完整落盘并返回读取路径，绝不截一半冒充完整文档；运行时文档变了就把新文档附加到结果里。单次失败立即 end_turn(interrupted) + 关连接——因为不知道那个点击到底执行了没有。

7

本轮结束：收尾（_finish_cua_turn）

用户取消则发 interrupt + endTurn(Interrupt) 并关闭连接；正常结束发 endTurn(Stop)，释放桌面锁，但连接保留到下一轮复用（REPL 里的 JS 变量还在）。

4. 会话与轮次生命周期

两个"轮次 ID"各管各的

字段谁生成作用
turn_id（宿主轮次）引擎贯穿同一宿主轮次的稳定身份，放在 metadata 的 deepseek/host-turn-id
runtime_turn_idf"{turn_id}:cua:{uuid4}"原生 runtime 眼中的"运行段"。每次重新取得桌面都换新的，因为 runtime 记得已结束的 ID，拒绝复活旧轮次

状态机（简化）

── 未连接 ──────────────────────────────────────────────
  connect()            成功 → 记下 instructions + 工具目录（必须是 js/js_reset，变了就报错）
── 已连接（空闲）───────────────────────────────────────
  call() 首次          取桌面锁 + 生成 runtime_turn_id
── 持有桌面（轮次中）─────────────────────────────────────
  call() 后续          复用同一 runtime_turn_id（REPL 变量延续）
  end_turn()           发 endTurn(Stop) → 释放锁，连接保留
  异常/超时/崩溃        endTurn(Interrupt) + close() → 整个丢弃，绝不带状态重连
── 关闭 ────────────────────────────────────────────────
  close()              发 close → 关 stdin → 5 秒等退出 → 否则 kill → 释放锁、清空一切

关键设计：不确定即丢弃。超时、桥进程崩溃、断连，任何"不知道动作执行了没有"的情况，都不重试、不重放，直接整段会话报废，下次重新观察。配套的 reset_reason 会在下一次调用时把原因告诉模型并强制重新观察。

5. 桌面锁：同一台电脑同一时间只有一个"手"

DesktopLease（session.py:21）用 flock 在 /tmp/deepseek-cua-<uid>.lock 上做跨进程互斥：

  • 锁的粒度是"轮次"，不是单次点击——从观察、操作到验证结果全程持有。注释原话："Hold through observe/action/verify, not merely through individual clicks"。两次工具调用之间的空档也不放。
  • 抢不到就 10Hz 自旋等待（可被取消）；O_NOFOLLOW 防符号链接劫持，fstat 校验属主，权限 0600。
  • 它只约束本适配器的会话之间（主任务 vs 子任务、多个进程实例），不阻止你本人或其他软件操作电脑——所以才需要第 6 节的"人工接管"检测。
  • 父任务派派子任务前先 handoff()：结束轮次、关连接、放锁，让子任务能接手桌面。

6. 人工接管与取消：覆盖"空档期"的监控器

难点：用户按"停止"或点"接管"时，模型可能正闲着（两次调用之间），也可能正卡在一个长操作上。session.run() + _watch() 组合覆盖两种情况：

空闲时发生接管

监控任务挂在取消/暂停事件上，事件一到：置 reset_reason → 发 interrupt + endTurn(Interrupt) → 关连接。下一次调用直接被拒，提示旧变量已失效、需重新观察。

操作进行中发生接管

监控器标记当前操作任务为"被打断的"并 cancel 它；操作内部把 CancelledError 翻译成 ToolError（"结果可能未知，重新观察后再继续"），同时触发 close。外部真取消（比如任务被杀）则原样向上抛。

两个细节值得点名表扬：

  • 初始化也能被打断——连接建立卡住 120 秒时按停止，立即中断，不用等超时（有专门回归测试）。
  • 等待人工授权不冻结控制通道——桥的设计让 interrupt/endTurn/close 不排队等一个正在等人点的调用；同时动作类请求的超时会在"有授权挂起"时暂停计时，但控制类请求照常倒计时（"人可以慢慢想，关机不能等"）。

7. 授权审批：三层不放大原则

原生 runtime 通过 elicitation 问"允许访问 X 吗"。Python 侧 approval.py 决定怎么呈现、怎么回答，处处fail-closed（认不出就取消）：

规则实现
只认两种形态原生应用授权（connector 为 computer-use + app ID）；浏览器授权必须 scheme://netloc 精确原始 origin（带路径的、非 http(s) 的、schema 带 required 字段的——全部取消）
宿主自我授权直接拒app 是 Workbench 自己（com.xingyuzhong.deepseekgui）时连问题都不出——防止模型给自己授权
范围不放大上游说支持 persist:["session"] 才显示"本次会话"选项；上游没给"始终允许"就选不了"始终允许"。回答映射回上游自己的语义，宿主侧的"会话级批准"不会变成上游的"永久授权"
子代理只转发单次子任务的授权卡片即使你在宿主选了"会话允许"，转达给 runtime 的也只是单次 accept——子任务没有资格开长期授权
默认取消超时、取消、异常、答非所问——一律 {"action":"cancel"}

9. 子代理协作：共享桌面，不共享 REPL

subagent.py 的 prepare_subagent_cua 给每个子代理建独立的 CuaSession：

  • 共享：桌面锁（同一把，谁持有谁用）、原生 runtime、授权体系。
  • 不共享：REPL（JS 变量隔离）、父任务的授权记录、宿主轮次身份（子任务有自己的 cua_turn_id）。
  • 父任务调用 agent 工具委派前先 handoff() 放锁关连接；子任务结果带 HANDOFF_NOTICE，明确告诉父任务"旧变量失效，重新观察"。
  • 子任务的取消事件链更长：自己的 token + 父的 cancel + 中断事件 + 父的暂停，全挂进监控器。
  • LCU 装不上、模型不支持视觉——子任务不启动 CUA 但不阻塞子任务本身，只在 metadata 里记 cua_error。

✅ 总体：设计合格，实现严谨，无阻塞缺陷

  • 33/33 专项测试通过（本机实跑验证），覆盖：桥接协议、权限范围、授权等待时取消、锁竞争、崩溃不重放、停止清理、工具目录、配置隔离、截图尺寸、退避、压缩提醒、子代理审批。
  • 文档（docs/CUA.md）与实现一致，且如实记录了验证边界（Linux / Chrome 页面操作 / 模型自主任务未覆盖）——没有夸大。
  • 测试是"真协议级"的：fixtures/cua/client.mjs 模拟 LCU 客户端记录调用序列，断言的是行为（ID 结构、Interrupt/Stop 事件、锁释放），不是实现细节。

⚠️ 三处边界观察（均不构成 bug，记录备查）

  • 授权在 0.25s 轮询片内完成仍计入动作超时（session.py:208-214）：超时冻结按 0.25s 粒度采样，一个起止都落在同片内的人工等待最多多扣 0.25s。上界固定且极小，可忽略。
  • _watch 竞态窗口（session.py:112-114）：操作在"检查未完成"与"cancel"之间自行完成时，结果正常返回而非报"被打断"。但 reset_reason 已置位，下一次调用必被拦下强制重观察——安全语义未破。
  • 锁等待无上限自旋：另一进程长期持锁时 acquire 以 10Hz 无限等待（可取消）。这是刻意的仲裁语义，不是缺陷；若未来出现多会话常驻，可考虑加公告/通知。

📋 已知的真实边界（来自 docs/CUA.md 自述，非本次审核发现）

  • Linux（X11）与 Chrome 网页内点击/输入未经真实运行时验证。
  • 脚本化集成测试 ≠ 模型自主完成业务任务的端到端验证。
  • CUA 无法阻止你本人在模型操作期间动鼠标——这正是"人工接管"路径存在的原因。
