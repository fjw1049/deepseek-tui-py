本地已有 message-display-report.md、subagent-status-report.md 且带未提交修改，本轮不覆盖。截图中另一组 report-A/report-B 文件没有在本次文件检索中找到，不把截图中的“全部核实通过”当成本轮结论。

## 2. 对已有任务的审核

### todo-list 优化

现有 InlineTodoBlock 已具备单层列表、原地更新、完成计数、取消单独计数、中文换行和完成默认收起。方向符合此前需求。

但独立组件漂亮，不等于接入主会话正确。当前存在已复现的集成问题：

- MessageTimeline.tsx:1523 的 shouldHideTodoToolBlock 隐藏 todoBlockIds 中全部工具块，包括首个 anchor。
- :1633 的 visibleExecutionBlocks 在展开过程时应用该过滤。
- :2157 本应将 anchor 渲染成 InlineTodoBlock，但该块此前已被过滤。
- :1146 的外层 InlineTodoBlock 只在 !workExpanded 时出现。
- 结果：有合法 checklist 数据的运行中会话，展开执行过程看不到计划，收起过程反而能看到。

本轮用 happy-dom 挂载真实 MessageTimeline 验证上述行为：busy=true、合法 checklist 快照，展开时卡片数为 0，点击收起后卡片出现。临时诊断测试已清理。该测试验证缺陷存在，不表示缺陷已修复。

### 主会话显示错误

历史任务已修正首段思考入口残留，并针对折叠后空白占位与手动滚动被重新接管增加回归检查。但历史任务也明确保留了整机现场验证边界。

当前另一个问题仍存在：message-timeline-logic.ts:228 的 isVisibleWithoutExecutionDetails 会保留所有有文本的 assistant 过程块，以及带 narration 的 reasoning。MessageTimeline.ui.test.ts 首个用例还明确要求完成后保留进度文字。

因此“最终答案前堆满检查、等待、核实的过程段落”符合当前代码规则，不会因隐藏“思考过程”标题而消失。需要修改产品规则和相应测试预期。

### subagent/task 侧栏需求

此前用户明确要求：主界面保留入口，点击后在侧栏查看执行过程；状态优先用转圈、绿色完成标记，不要重复状态文字。

当前主会话 SubagentSummaryPanel（MessageTimeline.tsx:1652）先展开内嵌列表，再从列表打开 RunPanel；TaskActivity 也提供任务入口。两处入口可以共存，但职责应明确：主会话记录本轮归属，活动区展示当前会话任务，详情统一进入侧栏。

折叠的 SubagentSummaryPanel 仅显示数量，状态计数和失败提醒都要求 expanded 才出现；结束后默认 Bot 图标无法区分全部成功与包含失败。这是读码确认的可见性问题。

## 3. 统一需求建议

目标：用户不读执行日志，也能知道计划是什么、哪些任务正在执行、是否需要介入、最后交付了什么；需要追溯时可展开完整记录。

| 信息 | 主会话默认展示 | 查看详情 | 状态来源 |
|---|---|---|---|
| checklist | 一张任务计划卡：完成数/总数、当前项 | 原地展开完整列表 | checklist 工具成功返回的结构化快照 |
| subagent | 紧凑入口：数量、必要的成功/失败/活动提示 | 单个直接开侧栏；多个先选任务 | 子代理生命周期事件及持久化状态 |
| task | 与 subagent 一致的入口交互，保留任务类型 | 统一运行侧栏 | Task 权威状态 |
| 过程进度文字 | 运行时突出最新有效进展；完成后收进过程区 | 展开按时间查看完整记录 | 已标注的过程消息 |
| reasoning / 工具日志 | 过程区内按需展开 | 保留现有可查看的详情 | 结构化消息类型 |
| 最终答案 | 独立正文，默认完整可读 | 文件链接和产物入口 | final_answer 标记 |
| 待审批 / 待输入 / 失败 | 保留可见的行动入口或失败摘要 | 详情中查看原因和日志 | 真实请求与错误状态 |

这是一套建议规则；其中“完成后收起所有历史进度文字”是本轮根据截图提出的设计收敛，不能写成用户此前已经逐项确认。

### checklist

1. 与“执行过程展开/收起”独立：任何状态下同一份计划只有一个展示主体，不能展开后消失。
2. 在首个有效计划建立后出现，状态原地更新，条目不因完成而重新排序。
3. 运行中默认展开；全部结束默认收起，仍可手动重新展开。完成数只统计 completed；取消不冒充成功。
4. 计划卡不因过程折叠而迁移到另一处重新挂载，避免丢失用户展开状态和制造高度突变。
5. 本次先按现有“每回合一份计划”处理；跨回合延续、新建第二份计划需要明确身份规则，不能仅凭标题相似自动合并。

### subagent / task

1. 用户应能直接识别 A、B 各自做什么。技术 ID 放详情，不占主标题。
2. 运行用转圈，成功用绿色完成标记，失败/取消/超时分别表达。无须在同一行再写一遍“运行中”；保留可访问名称与必要提示。
3. 聚合入口不能掩盖失败；一个在跑、一个失败时，两种事实都应可发现。
4. 主会话不铺开 spawn、wait、result、resume 的原始工具日志，详情统一由侧栏承载。
5. 关闭侧栏只关闭视图，不取消任务；父会话结束不自动等于子任务成功或结束。
6. 按 threadId、任务类型、实体 ID 区分记录；恢复同一实体是新执行轮次，不凭同一个 agentId 拒绝合法的重新运行。

### 主会话、状态与滚动

1. checklist 完成、两个子代理结束、父会话最终交付，是三个不同事实，不能相互推定。
2. 用结构化类型区分进度、推理、最终答案，不靠“我先……”等句子特征猜测。
3. 完成后只保留紧凑过程入口、计划/任务摘要、最终答案和产物；完整过程可回看，不能为简洁丢失记录。
4. 失败、待输入、待审批不能被折叠规则一并隐藏。
5. 重放、刷新、断线重连后应保持任务归属、顺序、最新状态一致；乱序旧事件不得覆盖新状态。
6. 用户向上查看后，迟到事件不能拉回底部。收起计划或过程时不能重新撑出整屏占位；侧栏更新不能驱动主会话滚动。

## 4. 两个截图案例的验收

### A：四项 checklist

- 首次写入后立即显示一张卡，依次推进 0/4 → 1/4 → 2/4 → 3/4 → 4/4。
- 每次完成在原卡原条目更新，无重复卡、闪现、消失或位置跳变。
- 执行过程展开和收起都能看到同一计划卡。
- 完成后卡片收起，展开仍可看到四项；三项完成、一项取消必须显示 3/4 与取消提示。
- 最终回答不被四段过程播报挤到页面底部；纯 mock 案例不额外要求真实创建业务文件。

### B：两个子代理完成分析并由父会话交付

- 主会话保留两个分析任务的紧凑入口，点击可在侧栏分别查看。
- A 完成、B 运行时，两者状态准确且同时可查。
- A、B 完成后，父会话仍可能在核验或写报告，不能提前把整个请求标为完成。
- 父会话最终交付后，默认正文突出结论与报告链接，重复的等待、取回、核验文字进入过程详情。
- 任一任务失败、取消或恢复，入口、侧栏、重载后的状态一致；报告截断与执行完成不能混为一谈。

## 5. 实施顺序与本轮验证

P0：修复 checklist 展开时不可见；明确完成后的过程折叠规则；保证待处理请求和失败可见。

P1：统一 task/subagent 紧凑入口与侧栏交互，补齐并行、恢复、迟到事件与重载一致性验证。

P2：统一卡片间距、字级、图标与轻量动效；以真实消息时间线验收，不能只看组件演示。

## 6. 实施记录（2026-09-20）

本节更新前述审核时的状态：已按用户“修复吧”实施主会话展示修复，并纳入后续“还有一些多余的信息没去掉”的截图反馈。

- 计划卡固定挂载在过程折叠区外；更新、收起/展开过程、完成时保持同一实例。
- 默认折叠执行过程；运行时只保留最新进展，完成后收起历史进度文字。
- 子代理单项直接开运行侧栏，多项展开紧凑任务列表后选择；不在主会话列表铺开工具日志。
- task 增加本回合入口，复用实时任务状态读取；只展示当前会话引用的任务。
- 任务入口统一运行、完成、失败、取消、超时图标；聚合运行状态不掩盖失败或取消。
- 父会话是否运行不再由子代理是否仍在运行决定。
- 待审批工具优先保留；失败工具在执行详情内有错误标记。
- 根据新增截图修正规则：历史 checklist/send_input/spawn 失败不逐行占据完成后的主会话。它们保留在执行详情；任务自身的失败状态仍在任务入口可见。此规则取代前文“失败工具优先留在默认视图”的宽泛表述。

### 后续调整：子代理只保留侧边入口

按用户最新反馈，移除主会话中的“Subagent N 个”和单个子代理入口。子代理状态、任务选择及运行详情继续通过已有侧边卡片提供；主会话展开执行过程也不重复显示子代理卡片。历史工具错误仍可在执行详情查看，待审批工具保留。本调整覆盖上文关于主会话保留子代理摘要的建议。
